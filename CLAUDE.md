# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is tracked in git (was previously local-only and drifted stale) — keep it current when you change architecture, add a service/route, or ship a release.

## Commands

- `./scripts/setup.sh` — Full setup: installs missing deps (uv, Node — accepts 22.22+ (react-router 8's engines floor, the highest of any dep; Node 20 is EOL), installs 26 fresh to match the image, and tries to upgrade npm to 12 to match the image's `ARG NPM_VERSION`, and now VERIFIES it took — on a Homebrew node the formula owns the `npm` symlink so a global upgrade is reverted by the next `brew upgrade node`, which the script now says outright rather than telling you to retry a command that cannot stick. Cosmetic for Docker deploys: the image installs its own pinned npm, Docker engine sans Desktop — colima/brew on macOS, get.docker.com on Linux), syncs backend+frontend, inits DB, builds SPA. Flags: `--docker-only` (just the engine, for the compose path), `--no-docker`, `--skip-build`
- `uv run uvicorn headroom.app:app --reload` — Run backend dev server (port 8000)
- `cd frontend && npm run dev` — Run frontend dev server (port 5173, proxies to backend)
- `cd frontend && npx vite build` — Production SPA build (output: `frontend/dist`, served by backend in prod)
- `cd frontend && npx tsc -b --noEmit` — TypeScript type-check (covers `*.test.tsx` too — they live under `src/`)
- `cd frontend && npm test` — Frontend unit tests (Vitest + Testing Library, jsdom). `npm run test:watch` to iterate
- `uv run pytest` — Run all tests (must run from project root)
- `uv run pytest tests/test_disposition.py::test_dispose_sets_fields` — Run single test
- `docker compose up -d --build` — Run as a Docker container (Pi-friendly)
- `docker compose -f docker-compose.yml -f docker-compose.mdns.yml up -d --build` — add LAN discovery (`headroom.local:8000`; host networking, Linux/Pi)
- `docker compose -f docker-compose.yml -f docker-compose.http80.yml up -d --build` — plain HTTP on port 80 via a Caddy sidecar (`http://headroom.local`, no TLS; password login only)
- `docker compose -f docker-compose.yml -f docker-compose.https-lan.yml up -d --build` — LAN HTTPS via Caddy's internal CA, so passkeys/Face ID work on `https://headroom.local`
- `HEADROOM_DOMAIN=hats.example.com docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build` — internet-facing HTTPS (Let's Encrypt)
- `… -f docker-compose.autoheal.yml` — restart the app when its healthcheck fails. **Docker's `restart: unless-stopped` acts on EXIT, never on `unhealthy`**, so the disk-floor and dead-worker checks readiness performs were a string in `docker ps` until something consumed them; this overlay (willfarrell/autoheal, needs the Docker socket) is one consumer and `scripts/headroom-watchdog.sh` (a systemd timer speaking HTTP, no socket) is the no-privilege other — `docs/OPERATIONS.md` §3 has both units. On the Let's Encrypt overlay the watchdog needs `HEADROOM_HEALTH_URL` pointed at the Caddy port, since `:8000` is not published there
- `… -f docker-compose.backup-rclone.yml` / `… -f docker-compose.backup-rsync.yml` — off-box backup upload after each scheduled backup (rclone bind-mounted; rsync over SSH with `HEADROOM_BACKUP_SSH_KEY`/`_KNOWN_HOSTS` mounted read-only)
- `uv run python scripts/restore-construction.py` — a one-off repair for the 2.11-era construction overwrite, run against a database file by hand; not in the image

## Architecture

**Backend** (Python 3.12+ — `.python-version` pins 3.14 locally to match the Docker image; FastAPI, SQLAlchemy async + aiosqlite):

In order: the single-process guard, `init_db`, the branding seed, then the flagged one-time backfills (`vocabulary_merged_v1`, `retail_prices_v2`, `model_names_split_v1`, `color_names_normalized_v1` — each a row in `app_settings`, so it runs once per database rather than once per build), the no-owner warning, then the long-lived tasks: the scheduled-backup loop, the re-pricing scheduler (`repricing.start_repricing`), the bulk-import worker, the **analysis worker**, the thumbnail backfill and the export-derivative backfill (`_backfill_exports`, which waits for the thumbnails), mDNS advertise, the daily activity-log/session prune, and `_tls_watch_loop` (boot + daily: `tls_health.check_certificate` and `ca_vault.check_root`, so the CA fingerprint is seeded at boot rather than the first time somebody opens Settings → Device). Then CORS, SPA serving with path-traversal protection. **This list is the code's order and is the thing to update when a loop is added** — a stale roster here is how `_tls_watch_loop` went undocumented for a release

That field is the gate for **both** purchase matching and product pricing, and one foreign token (`camo`, `808`, `watercolor`) makes a hat unmatchable against its own receipt AND unpriceable against its own product — so the "bad matching" was never the matcher, which is provably optimal under its gate; the gate was being fed corrupted input. Measured against the 568 harvested products: **89 of 235 model names matched no melin product**, 35 carried a literal separator. The prompt now states the naming convention and forbids a separator in `model_name`; `hat_analysis_pipeline._split_model_and_colorway` repairs one defensively, and **only a SPACED separator counts** — `A-Game` is a line and the most common one in the collection, so a naive split on `-` yields `("A", "Game Hydro")` and breaks every A-Game hat, which is worse than the bug. `backfill_split_model_names` repairs stored rows once from lifespan behind `model_names_split_v1` (same reasoning as `retail_prices_v2`: fixing the schema alone leaves the name depending on *when* the hat was analyzed); splitting alone took usable names **146 → 174 of 235** with no API call. An analyzer colorway is applied by `_apply_analyzed_colorway` only when `catalog_service.is_real_product()` confirms the pair against the harvested catalog, and **never over an existing one** (that came from a receipt or the owner, both of which outrank a photo). **That validator's two halves are NOT symmetrical, and it has now been wrong in both directions** — the model is `hat ⊆ catalog` (a photo cannot show the sub-line, so the name lands on the family), but the colorway is **token-set EQUALITY**. Containment on the colorway is a leak whichever way it points: `catalog ⊆ hat` accepts `Hawaii 808 Camo` against a catalog holding only `Camo`, and `hat ⊆ catalog` accepts `Camo` standing in for `Rain Camo`. **Single-word colorways are the common case** (Camo, Black, Navy, Bone) and each one validated anything containing it. This is not a cosmetic false positive: whatever survives gets WRITTEN, and a stored colorway is a **veto** in `_match_score`, so an invented one rules the hat out of its own receipt — the feature made matching worse in exactly the way it existed to fix. It survived a review because the fixture colorway was `Deep Dive`: at two tokens, containment happens to fail, so the test could not see the shape production actually has. Validation is deliberately a filter applied AFTER, not a candidate list sent WITH — the same reason `_known_series_context` is framed as a record rather than a menu: a menu invites a forced choice, a validator can only reject. `_owner_context()` carries the owner's stated facts AND `_known_series_context()`, the collab/artist-series names already in the collection. Those are sent because **a series is rarely legible in a photo** (a woven label, an embroidery style), so an analyzer recalling them unaided misses most of them. Framed as a record of what the collection contains, **not** a menu — a candidate list invites a forced choice and a wrong series is indistinguishable from a right one, so the prompt says `null` beats a wrong match. Truncation past `MAX_KNOWN_SERIES` is stated in the prompt, never silent

  - `melin_recap.py` — Melin resale: deep links + live median asking price via the Sharetribe Flex public API (melinrecap is a Treet marketplace; anonymous public-read token, client id in config, `query_listings` is the test seam). Degrades to link-only on API failure. **`query_all_listings` PAGINATES, and that is a correctness fix**: the query used to send one request and take what came back, but the `odysea` category holds **436** listings, so it read 23% of the market and priced every Odysea off whichever quarter the API returned first — `meta.totalItems` was in every response and discarded. It terminates on a short page rather than reading `meta`, keeping `query_listings` as the single seam tests already patch. **`model_tokens` strips punctuation and is applied to BOTH sides** — splitting on whitespace left it glued on, so `Odysea Hydro "Have More Fun"` demanded the tokens `"have` and `fun"`, which appear in no listing title ever, and the hat fell silently to a category median. **melin's own PRODUCT is tried FIRST, and that is the fix for hats all sharing one price** (`_product_comp`). Every listing publishes `shopifyProductName` ("Trenches Icon Hydro - Prismatic") and a structured `selectedVariantOptions.color` — **986 of 986 listings across 510 distinct products** — and pricing ignored all of it to token-match the freeform `title`. melin names goods `<Model> - <Colorway>`, which is exactly the two columns a hat carries, so matching those prices a hat as ITS OWN ITEM. Measured on the real collection: the top five prices covered **168** hats before and **135** after (the 54 at exactly $85.00 were unchanged by this — those are the colorway-less hats `shared_price_audit` exists for), and the number of distinct prices went from 5 to **33**. An earlier version of this sentence claimed the five-price cluster went to 33, which conflated the two figures; CHANGELOG 2.71.1 carries the correction. **A colorway is REQUIRED** — without one there is no product, only a line, and calling that a product match is how `Odysea Hydro` matched 319 listings across 131 products; matching more than `_MAX_PRODUCTS` is a line too. **No minimum sample**: on a fixed-price marketplace one live listing of THIS product beats the median of a line it merely belongs to, and `count` is published so thinness is visible. **A stated construction VETOES a rival product** (`_rival_construction`), since Icon Hydro and Icon Thermal are different goods at different prices. Two things are load-bearing and 2.71.0 got both wrong. **Only the MODEL half is read** (`product.split(" - ", 1)[0]`): `Denim`, `Canvas`, `Suede`, `Linen` and `Corduroy` are constructions AND common colorway words, so reading the whole string made `Trenches Icon Hydro - Denim` look like a Denim product and vetoed a HYDRO hat from its OWN item — a correctly recorded construction made pricing WORSE than leaving it blank, the exact inversion of the point, and the same `denim`-in-the-colorway-half trap this file already documents for `catalog_service`. **It vetoes on CONTRADICTION, not absence** — a product whose model half names no construction contradicts nothing; vetoing on absence rejects almost everything. HYDRO/HYDROLite veto each other correctly (token equality, not substring). A **blank** construction vetoes nothing (nobody has looked). The source sentence names only the products in the rows that actually SET the number, computed after the condition/size narrowing — before it, a hat priced by one listing was labeled with three, including a Thermal that had no part in it. **Sold history does not exist**: the API ignores `states=closed` and returns the same open listings, so live asks are the only signal. The title ladder below is the FALLBACK. **Model specificity is surrendered ONE TOKEN AT A TIME, and entirely, before condition or size are given up at all.** melin titles read `<line> <construction> - <colorway>` and `model_name` comes from Claude reading a PHOTO, so the leading tokens are the product line and the trailing ones are whatever artwork was visible; dropping the last token steps from "this exact design" to "this line", which is a real comparable. There was no such rung — it went straight from "every token matches" to the median of the whole category, which is how **28 hats all sat at exactly $115.00**. Condition is kept while the model is shortened because condition is a FACT off the listing and the model prefix is a guess about naming. **A prefix is a `model` match only if it matched the whole name OR actually narrowed the field** — token count cannot decide this, since for an `a_game` hat the prefix `a game` has two tokens and still selects the entire aGame category, so `narrow(())` is compared against and the answer comes from the data rather than the name. The source label **names the line matched** (`median of 18 live classic new-with-tags Odysea Rope Hydro listings`), because after prefix-shortening "model listings" would hide *which* model.
  - `repricing.py` — **Periodic re-pricing, deliberately INDEPENDENT of analysis.** Until 2.64 `refresh_melin_resale` was reachable only from inside `hat_analysis_pipeline`, so a hat's value moved only when that hat was *analyzed* and nothing re-checked prices on a schedule. On the real deployment every appraisal sat frozen at the date of the last bulk re-analysis — weeks — and the only way to move them was to re-analyze the whole collection, spending a Claude vision call per hat to fetch a marketplace median **that needs no Claude at all**. The coupling also chained two unrelated failures: when the Anthropic balance ran out, Claude raised, the pipeline fell back and **returned early**, and the price refresh below it never ran — so prices stopped because *identification* stopped. `fetch_resale_stats` keys on `style`/`model_name`/`condition`/`size`, all already columns, so re-pricing needs no photo, no key and no vision call. **`manual` scope is excluded in the QUERY as well as inside `refresh_melin_resale`** — the inner guard makes the write safe, the outer one makes a protected hat cost no API round trip. Disposed hats are excluded (they have left the collection). **Ordering is oldest-`resale_checked_at`-first, nulls first**, so a sweep cut short by a restart or `HEADROOM_REPRICING_BATCH_LIMIT` makes progress on the stalest prices instead of re-doing the freshest forever. Commits per hat — a sweep is minutes long and a restart mid-way must not discard all of it. **`reprice_once(session_factory=...)` takes the factory as a seam**, because reaching for the module-level `async_session` is the same mistake `error_handler` documents: it works in production and silently talks to the wrong database in every test. `RepricingHealth` is process-local and correctly so — the durable answer is already per-hat in `resale_checked_at`. **`last_repriced` counts prices that CHANGED, not hats visited**: a sweep that checks 234 and moves none is a working sweep, and reporting the visit count would make a flat market look like busy work *and* look identical to a sweep silently failing to write. **`POST /api/admin/repricing/run-all` is the whole shelf, in the BACKGROUND** — 202 + `asyncio.create_task`, because the bounded inline run below was the only option and re-pricing everything therefore meant pressing repeatedly or waiting 24h for the scheduler (the same "reachable only from inside a bigger operation" gap `catalog_service.unclaimed_from_purchases` documents). It **refuses a second sweep while one runs** — `_sweep_lock` would serialize them, but queueing a second full pass is never what the press meant and one progress bar cannot show two runs; `started`/`already_running` are separate booleans because "not started" has two meanings. **`create_task`, NOT a FastAPI BackgroundTask, and the difference follows from holding a claim** — Starlette runs background tasks only after the response body is sent, so a send that fails means the task never runs, nothing releases `_full_sweep_claimed`, and BOTH routes are dead for the life of the process (this one refuses every press, `/repricing/run` 409s forever) with no way back but a restart. The colorway harvest used to be the counter-example (a BackgroundTask, because it claimed nothing) and no longer is: it claims a slot too (`claim_harvest`) and so runs under `create_task` for exactly this reason, its tasks held in `_running_harvests` — the guard outlives the work it guards in both. In-flight tasks are held in a module-level set, since asyncio keeps only a weak reference and a collected sweep never reaches its `finally`. **Every full sweep claims the slot, the SCHEDULER included** — the claim was written for two presses of one button and never asked what else takes `_sweep_lock`. `_loop()` does, for minutes, every cycle, unattended, and while it ran the slot read free: "Re-price all" would start a second full pass (the one thing it promises to refuse) and "Re-price now" would skip its 409 and block on the lock for the whole nightly run, which is the dead spinner its own cap exists to prevent. A guard only one of three callers respects is not a guard. Failures are recorded (nobody watches a background sweep) and it uses `scheduled=False` like the inline run. The card invalidates hat views on the **true→false edge of `running`**, never in `onSuccess` — a 202 arrives long before a price changes, and that edge also catches the scheduled sweep finishing. `POST /api/admin/repricing/run` works even when the scheduler is disabled — turning the background task off must not remove the ability to refresh on purpose — and is **BOUNDED to `MANUAL_SWEEP_LIMIT`**, because uncapped it is a four-minute inline HTTP request: a dead spinner on a phone, then a proxy timeout, after which the result is discarded and nothing is recorded. It reports `remaining` (a SQL COUNT, never `len()` of the capped list) so the card can say press-again rather than leave "50 of 234" reading as a failure. **`record_success(..., scheduled=)` — a MANUAL run must not clear `last_error` or `consecutive_failures`**: those belong to the scheduler, and a sweep failing nightly for a month otherwise read "swept just now, 0 failures" after one click, hiding exactly the dead-task condition the record exists to expose. A failing manual run calls `record_failure` and re-raises. **`_sweep_lock` serializes the loop and the button** — two doors into the same few-hundred sequential calls, and pacing each politely while allowing two at once is a courtesy that only looks like one. **The sweep stamps `resale_checked_at` on EVERY attempt, not just successes**: `refresh_melin_resale` returns early for a non-melin brand, an API error or an empty result, so those hats kept a NULL timestamp, and under `nulls_first` they owned the head of the queue permanently — a capped sweep re-visited the same never-priceable rows forever. Safe against `price_audit`, whose `was_market_priced` hint reads that field, because that report covers only `manual`-scope hats and this sweep excludes them.
  - `catalog_service.py` — Colorway catalog harvested from melinrecap listing titles ("Model - Colorway", `parse_listing_title`); purchase-history import + hat matching (sets hat.colorway/purchase_price/purchased_at). **The harvest isolates each category**, and the clause doing it catches `Exception`, not just `MelinRecapError` — narrowing it to the API error covered the failure that was in mind when it was written while the stated property is broader, so a racing harvest's `IntegrityError`, a disk error mid-commit or a decode failure on a title still killed the whole run. `Exception` and not `BaseException`, so a shutdown's `CancelledError` stops the sweep instead of being filed as one flaky category. **`harvest_in_flight()` is `claimed OR running` and is published as `CatalogStatus.in_flight`** — `progress.running` is set inside the background task while the slot is claimed in the request, so a card watching only progress re-enables its button during the gap and the next press is refused for reasons it never showed; that accessor existed with no caller while the card papered over the same gap with a 30-second wall-clock guess, which was also purely local (a harvest started on a phone left the laptop's button live). Originally: `query_listings` raises on any non-200, and one 429 used to abandon every category after it — sequential sweep, commits per page, endpoint already returned 202, so the result was a *silently* partial catalog indistinguishable from a complete one. `_fetch_page` retries with backoff; a category that still fails is recorded in `failed_categories` and the sweep continues. **`GET /api/admin/colorways/status` reports what is actually in the catalog** — the Settings card used to show `len(GET /api/meta/colorways)`, which is the AUTOCOMPLETE feed capped at `catalog_options`' default `limit=25`, so it read "25 models known" no matter how much had been harvested. `_units_to_add` is the single dedupe decision shared by import and preview. Endpoints: POST /api/admin/colorways/refresh, GET /api/admin/colorways/status, /api/admin/purchases/{import,match} (both take `?dry_run=true`), /api/admin/purchases/{id}/unmatch + /purchases/unmatch-all, GET /api/meta/colorways (autocomplete — **takes an explicit `limit`, defaulting to 1000 so it serves the WHOLE catalog**. It passed none, so it took `catalog_options`' default of **25**, and the picker offered 25 of 188 harvested colorways; `EditHatPage` fetches this feed *without* `q` and the combobox filters client-side, so everything past the cap was unreachable however specific the query. Reported as "the catalog is missing so many colorways" when the harvest was complete and same-day. This is the SECOND time the 25-cap has been mistaken for a small catalog — the first was the Settings card reading `len()` of this feed, fixed by `/api/admin/colorways/status` — because **a truncated list is invisible: it looks exactly like a short catalog**. `test_the_colorway_picker_can_reach_the_whole_catalog` asserts the tail specifically, since the entries a cap removes are the ones nobody notices are gone. **Model matching is TOKEN-SET CONTAINMENT, not equality**, for the same reason `_match_score` uses `MODEL_CONTAINED`: under equality a hat named for the family saw ZERO colorways at any limit, so lifting the cap alone did not fix the reported symptom — the picker looked empty and the catalog looked incomplete. Asymmetric like the matcher: every token of the requested model must appear in the catalog entry's token set. SET containment, decided in Python after a cheap `ilike` prefilter, not `ilike %token%` per token — the substring form matched `hydro` inside `hydrolite`, so an `A-Game Hydro` hat was offered HYDROLite colorways, the same product confusion the construction filter guards against). **Unmatch is the undo matching never had** — it mutates hats and only reconsiders purchases with a NULL hat_id, so a wrong link was permanent and invisible (the hat still got *a* price and *a* colorway). `_revert_hat_fields` clears a field only when it still holds the value match wrote; anything edited since is somebody's deliberate value. `unmatch-all` keeps the purchase rows — re-importing years of orders is the expensive part. Route order matters: `unmatch-all` registers BEFORE `{purchase_id}`. **Matching is scored, not first-hit** (`_match_score`): size outranks colorway, a stated field that disagrees rules a hat out, ties are reported not guessed. **The MODEL is the gate and only the model** — a hat matches on exact token equality (`MODEL_EXACT`) or when its tokens are a **subset** of the purchase's (`MODEL_CONTAINED`, scored far lower), because `model_name` comes from Claude reading a PHOTO, which cannot show the sub-line, so it lands on the family (`odysea hydro`) while the receipt states the product (`Odysea Packable Hydro`). Asymmetric on purpose: a hat named *more* specifically than the receipt does not match, or one generic line claims any specific hat in the family. Everything else SCORES — owner-stated `artist_series`/`construction` (compared against the WHOLE title, since melin puts the series in either half: `Trenches Links Hydro` vs `Trenches Icon Hydro - Camo`) and the analyzer's color words against the receipt's colorway. Bonuses, never vetoes: 102 hats have no series and absence is not disagreement; putting them in the *gate* was tried and measured **worse** (143 → 105). **Assignment is MAXIMUM bipartite matching** (`assign_purchases`, Kuhn's augmenting paths), not greedy. Greedy-with-`_by_scarcity` was measured leaving 3 real matches unclaimed the moment scoring changed — the property it appeared to have was luck, and ordering was the trick that bought it. Augmenting paths cannot have that failure: a later purchase displaces an earlier one and sends it to another hat it also fits. Candidates are visited in DESCENDING SCORE order, so among maximum-size assignments the better-evidenced pairings win; cardinality is guaranteed, score is the tiebreak. Keyed on `id(hat)` not `hat.id`, because `preview_import` scores TRANSIENT rows whose PK is still None. **Both the importer and `preview_import` call it**, or the preview under-reports what the button does. **`_by_scarcity` is GONE, and its removal is the cautionary tale in this file.** It ordered purchases most-constrained-first back when assignment was greedy; Kuhn's replaced greedy and left it with no call site — while this document, its own docstring and a test docstring all went on describing it as the thing carrying the result. Cardinality under Kuhn's is order-independent, which is precisely why nothing failed when the ordering rotted. **When an algorithm is replaced, the prose explaining the old one is what survives.** On the real 294-unit history this went 41 → 144 → **152** matched, which is the **maximum bipartite matching _under the current gate_** (216 of the 294 lines are actual hats; the rest are travel cases. 19 unmatched lines have no candidate hat at all — those are hats not on the shelf, not matcher failures). **The gate retries with the CONSTRUCTION word stripped from both sides**, because melin names read `<line> <construction>` and a receipt may put that word in either half of the title: hat "Eagle Denim" vs "Eagle Mill Union - Hickory Denim" failed containment on `denim` sitting in the colorway half. The tests executed the scoring and constrained none of it. `tests/test_matcher_evidence.py` is the fix and the model for the fix: every test there asserts an OUTCOME (which purchase got linked, what price landed on the hat), never a score, and each docstring names the mutation it was written against. **To probe a module**: change one constant or delete one call, run the suite, and if it stays green the code is covered and unconstrained — the shape that produced a $999 cost basis where $79 was provable. Not in CI (a full mutation pass is hours and Actions credits are finite); run it by hand when touching anything that writes a number. Two mutations that survive legitimately: reversing the purchase iteration order (`_improve_by_swapping` now carries the result, so the order is a fast path — see the comment in `assign_purchases`) and swapping the `manual`/`comp` branches in `valuation.value_hat` (a hat has one scope, so the branches are exclusive and the mutant is equivalent)
- **Do not write a per-endpoint "requires auth" test.** `tests/test_security.py::test_every_api_path_is_gated_unless_it_is_on_the_allowlist` enumerates `app.openapi()` and probes every operation anonymously, so one more `assert ... == 401` for one more path adds nothing it does not already check — fifteen of those were removed in 2.77.1, spread across twelve files, none of which would have caught the `/openapi.json` leak because nobody had written one for that path. A NEW open route goes on that test's allowlist, which is a decision somebody has to write down. The two exceptions stay: `/uploads/` is a mount and `/openapi.json`/`/docs`/`/redoc` are not in the spec they describe, so neither is reachable from the enumeration

**Frontend tests** (Vitest 4 + Testing Library 16, jsdom):
- Co-located `*.test.tsx` beside the component. `src/test/setup.ts` registers the jest-dom matchers + `cleanup`; `src/test/utils.tsx` exports `renderWithProviders` (fresh QueryClient per test, `retry: false`, plus MemoryRouter)
- Vitest config lives in the `test` block of `vite.config.ts` (imported from `vitest/config`) so tests inherit the plugins and the `__APP_VERSION__`/`__BUILD_SHA__` defines instead of a second config that can drift
- `src/test/fixtures.ts` holds the shared `hatFixture()` — `HatRead` has ~50 required fields, so without it every test writes the whole literal and adding a column breaks each copy independently. `renderWithProviders(ui, { route })` sets the MemoryRouter's initial entry, needed by anything reading `useParams` / `useSearchParams`
- API modules are `vi.mock`ed at the module boundary — **mock the real payload shape**: pydantic serializes fields with defaults, so `ApiKeyStatus(configured=False)` is `{configured, source: null, masked: null}`, not `{configured}` alone. `tsc` catches the mismatch because test files are inside `src/`
- Query controls **must** carry `aria-label` (the visible `<label>` elements have no `htmlFor`, so nothing else associates them). This is an accessibility requirement first and makes `getByLabelText` work as a side effect
- `src/routing.test.tsx` pins the react-router behavior the route table relies on (pathless layout routes via `Outlet`, public routes outside the shell, static-over-dynamic precedence, `useParams`/`useNavigate`/`useSearchParams`) — added with the v8 upgrade so "the breaking changes don't apply to us" stays a checked claim
- Count not quoted, same reason as the backend suite above.

## Key Patterns

- **Async relationship loading**: Always use `selectinload()` for relationships; after commit + relationship changes, call `db.expire_all()` then re-query (see `_reload_hat()`, `_reload_case()`). `expire_all()` is **synchronous** on `AsyncSession` (no `await`), and `run_sync()` takes a **sync** callable — passing an `async def` fails at runtime, not at import
- **Database migrations**: `database.py:_run_migrations()` runs `ALTER TABLE` against existing DBs using **fully-static** DDL strings (no f-string interpolation into `text()`); `_HAT_COLUMN_DDL` is the source of truth for hat-column additions. `tests/test_schema_consistency.py` enforces that EVERY `Hat` model column is covered by the DDL (a forgotten entry bricks every hat read on an upgraded DB). New TABLES need no migration — `Base.metadata.create_all` creates any the models declare — while new COLUMNS on an existing table do, which is what `_HAT_COLUMN_DDL`, `_CASE_COLUMN_DDL`, `_HAT_COLOR_COLUMN_DDL` and `_PURCHASE_COLUMN_DDL` are for (`tests/test_schema_consistency.py` covers the hat and purchase lists). `_STATUS_RENAME_DML` is the one data migration, three static `UPDATE`s that rewrite the old British `cancelled` status to `canceled` on every boot (idempotent, so a downgrade-then-upgrade cannot strand a row)
- **`logo_detected`** records what the analyzer SAW (mark + owning brand); `brand` may be inferred. Set by Claude (tool-schema field, required, null allowed) and by the Google Vision fallback.
- **Analysis-written free text is canonicalized too.** `vocabulary.canonicalize` ran only in `hat_service` (the client PUT/POST path); the ANALYSIS path wrote straight through, so Claude returning `skye walker` created a second entry beside the owner's `Skye Walker`. Invisible by construction — both hats have *a* series, and the split shows only as near-duplicate rows in the autocomplete, the Stats collab chart and the filters. `hat_analysis_pipeline._canonicalize_analysis_text()` runs after `_apply_analysis` on BOTH call sites and covers `artist_series` plus a construction Claude filled in; construction goes through `set_construction` so the derived flags can't drift
- **Owner-stated facts are sent to Claude as ground truth**: `claude_analysis._owner_context()` builds the prompt sentence from `selected_style` AND `selected_construction`. Protecting the stored value is not enough — before 2.17 the construction was never sent, so a hat recorded as Thermal came back with `model_name='A-Game HYDROLite'`: right field, wrong name in the one a person reads. `_strip_contradicting_construction()` also removes a rival construction from `model_name` on every analysis, so a full rescan repairs old rows (removes rather than substitutes — "A-Game Thermal" would be an invented product name; "A-Game" is less specific and true). Word boundaries are load-bearing: `HYDRO` must not match inside `HYDROLite`
- **Analysis NEVER writes construction — it is owner-only.** `_apply_construction` is a documented no-op. It used to fill a blank, and that was the same coin toss as the 2.11 override it replaced: Claude reads HYDRO vs HYDROLite off one photo unreliably (bonded seams / gel-welded logo / sweatband don't survive a front-on shot) and skewed HYDROLite. Two later changes made a guess expensive — `retail_pricing` prices HYDRO $79 vs HYDROLite $99 (**it moves money**), and 2.29 made construction a filter (**it hides hats**). A blank is an honest "nobody has looked"; a guess is indistinguishable from a typed value, and no column records which it was. **`_strip_contradicting_construction` strips ALL constructions when none is stated** — melin names read `<line> <construction>`, so a name is the same claim in the field a person reads, and the old early-return meant a blank protected nothing. `services/construction_audit.py` + `GET/POST /api/admin/constructions/{audit,clear}` undo what was already written: a report and an explicit `dry_run` action, NOT a backfill, because which stored values were guesses is unknowable retroactively. Clearing also drops the model-name suffix and a `melin retail` price derived from it (a Manual price is never touched)
- **Hat construction**: free-form text (`Hat.construction`) with structured suggestions, NOT an enum — melin ships specialty fabrics in seasonal/collab drops, and a closed list makes each one unrecordable until someone ships a migration. `hydro` / `hydrolite` remain real columns because search filters query them and a `@property` can't appear in a `WHERE` clause, but they are **derived**: `Hat.set_construction()` is the only writer of all three, and assigning the flags directly is what lets them drift (a hat reading "Thermal" still matching a HYDRO filter). Substring match, HYDROLite checked first since it contains "hydro". Pre-2.11 clients still sending the booleans are folded in — at the schema for `HatCreate`, in `hat_service.update_hat` for `HatUpdate` (which needs the hat's current state, because `{"hydrolite": false}` means "not HYDROLite", not "no construction"). Suggestions: `GET /api/meta/constructions` merges `KNOWN_CONSTRUCTIONS` with the distinct values in use
- **Upload caps**: `copy_upload_capped` (strict, 413) guards the two single-file photo routes — the hat photo and the logo (the case photo was the third and no longer exists) — and `copy_upload_truncating` (lenient) guards bulk import. **Both stream to disk; neither buffers a file in memory.** The lenient one was `read_capped`, which accumulated chunks and returned bytes — and the import route never called it, carrying a private `_spool` that streamed instead. Two correct implementations, so nothing failed and only this line was wrong; the streaming one is now the only one, and it spools under `import_service.spool_dir()` (beside the uploads, on the same volume) so staging into a job is a rename rather than a second write. `POST /share` spools each file to a temp dir in capped chunks and hands `create_job` **paths**. It previously read whole files into memory AND passed bytes — which `create_job` cannot use (`source.stat()`, `shutil.copy2(source, …)`), so every Android share raised AttributeError on the first file. Unbounded and broken, with no test covering the handler, which spools each file to disk as it arrives rather than buffering the batch. Peak RAM on any upload path is one chunk or one file, never a collection
- **`owner_notes`** is the only free-text field on a hat that no automated path writes — not analysis, not a refresh, not a bulk re-analyze. Every other prose field (`design_notes`, `style_descriptor`, the color names) is derived and gets rewritten, so the card says outright that this one survives
- **`CONDITION_LABEL` lives in `lib/valuation.ts`** in TWO casings that are deliberately different, not duplicates (only `CONDITION_LABEL` is exported; `CONDITION_IN_SENTENCE` is module-private and read by the sentence built beside it): `CONDITION_IN_SENTENCE` (lowercase, goes inside a sentence) and `CONDITION_LABEL` (title case, for chart legends and table rows). Stats and Valuation each had their own copy, one named `CONDITION_LABELS` — differing from the other by a single trailing `s`
- **Adding a Hat column**: model + `_HAT_COLUMN_DDL` + `HatRead` + `types/index.ts` (+ `HatUpdate` if the UI edits it). Skipping a step is silent: a column missing from `HatRead` is invisible to the UI, one missing from the DDL bricks every hat read on an upgraded DB, and one missing from all of them is just dead weight (`custom_style_detail` sat unread from the initial commit until a review found it). There is deliberately **no** hand-written ORM→schema mapper: `HatRead` is `from_attributes=True` and `routes/hats.hat_to_read()` is just `HatRead.model_validate(hat)` (public, since the share-target and import routes build the same read). Values that aren't columns (`wear_count`, `case_display_id`, `case_type`, `room_id`, `room_name`) are `@property` on the `Hat` model beside `display_id`, so nothing outside the model walks `hat.case.room`. `tests/test_hats.py::test_hat_read_exposes_every_derived_field` pins all of them plus the unassigned-hat null case
- **SQLite tuning**: WAL + `busy_timeout` on connect (`database.py`), so a transient `database is locked` waits rather than raising — important for the import worker + background loops on a Pi. **`synchronous=FULL`, reversing the earlier `NORMAL`.** `NORMAL` is SQLite's own WAL recommendation and is safe from CORRUPTION, which is what most guidance means by safe — it is NOT safe from LOSS: the WAL is synced at a checkpoint, not at commit, so a committed transaction "might roll back following a power loss" and the default 1000-page threshold means what is at risk is every write since the last checkpoint, not the last one. This deployment proved it is not theoretical: an unclean shutdown destroyed Caddy's private key on the same SD card and broke HTTPS for 37 days. `FULL` costs one fsync per commit, which for a personal inventory doing a handful of writes per interaction is not a close call. `HEADROOM_SQLITE_SYNCHRONOUS` overrides it; anything outside `SYNCHRONOUS_MODES` falls back to `FULL` rather than through, because the value is spliced into a PRAGMA (which cannot take a bound parameter) and a typo must not quietly disable durability. `checkpoint_wal()` runs LAST on shutdown — the workers above it still commit as they stop
- **Single-process by design**: rate limiter, passkey challenge store, import queue, **analysis queue**, token caches, mDNS singleton are all in-memory and process-local. `>1` worker silently breaks passkey login/rate-limiting/import dedup; the lifespan warns when `WEB_CONCURRENCY`/`UVICORN_WORKERS`/`GUNICORN_WORKERS` > 1
- **Valuation is ONE rule, in `frontend/src/lib/valuation.ts`**. It was three (home page, valuation page, `report_service`) and all three had drifted — the home page's caption named multipliers that by then applied to almost nothing, and the report labeled a scraped median "manual". **The listed price IS the sale price**: melinrecap is a fixed-price Treet marketplace with automatic drops, so nothing is discounted off it. Comparability comes from FILTERING, done upstream in `melin_recap.fetch_resale_stats`, which matches listings on the hat's own condition and size (both are in `publicData` and were ignored until 2.21) and widens most-specific-first only when the sample is too thin. The `ASK_TO_SOLD` haircut and `CONDITION_VS_MARKET` multiplier this replaced were measurably wrong against 706 live listings and unnecessary with the real number in the feed. Signal order is `manual` (used as-is) → `comp` (model+condition+size median, used as-is) → `retail` (`RETAIL_RETENTION` share of new — still a heuristic, but only when there is no market data) → `category` → `none`. `retail` deliberately outranks `category`: retail is about THIS hat. `valueHat` returns `null`, never 0, for an unpriced hat. `CASH_PAYOUT` (0.80) / `CREDIT_PAYOUT` (1.10) are what the marketplace pays a SELLER, read off `publicData.payoutInfo`; market value and what reaches you are different numbers. `services/valuation.py` mirrors it for the server-rendered report — **including `value_cases()`**, which was first written into `report_service` as a THIRD statement the parity check could not see, and had already drifted (flat constant per row vs the browser summing each case's served `retail_price`); `tests/test_valuation_parity.py` fails if they diverge
- **`resale_price_scope`** (`manual`/`model`/`category`) records what `resale_price` is a price OF. `resale_price_source` says the same thing inside a display sentence, and branching on prose would silently revalue the collection the day someone reworded the label. `manual` is set by `hat_service.update_hat` (the one writer every client PUT funnels through; the value is `models/hat.ResaleScope.MANUAL` — a `StrEnum`, so the three scopes are compared by name rather than by three copies of a string) and makes the price immune to analysis overwrites — both `refresh_melin_resale` and `_apply_resale_pointer` bail on it. That second one mattered: it assigned the pointer's `None` price unconditionally and relied on the live refresh restoring a number, so an outage during an unattended re-analyze silently erased hand-entered prices
- **Find duplicates**: `services/duplicate_service.py` + `GET /api/search/duplicates` + `/duplicates` page. Groups ACTIVE hats on identity fields, never pixels (two shots of one hat differ; two different hats in one colorway don't). `exact` = every field agrees; `likely` = same model+size with the colorway missing on a side — colorways that actively DISAGREE are never grouped, or every normal shelf reads as a mistake. Requires a model_name (or brand+colorway) or un-analyzed hats all match each other. Reports only; never deletes
- **Dropdown lists must be portalled**: `components/common/AnchoredList.tsx` renders picker lists into `<body>` via `portalToBody` and positions them against their input. A list positioned inside the form is CLIPPED by `.card { overflow: hidden }` — cut off mid-row, options below unreachable, and no z-index helps because the pixels are never drawn. Two consequences of leaving the tree: hold the anchor in STATE (a ref is null on the render that first opens the list) and treat `.hr-combobox-list` as "inside" in the click-outside handler, or pointerdown on an option closes the list before the option's mousedown lands. Heights measure against `visualViewport`, so the list clears the keyboard
- **Case picker ordering**: the 3 newest cases are pinned above the room groups (`RECENT_COUNT`) and removed from those groups so nothing lists twice; suppressed once a query is typed
- **Cases show a collage** of their hats, not a case photo — every case looks the same from outside, so the picture carried no information. `components/cases/CaseCollage.tsx` is the single component; the grid feeds it `CaseRead.hat_thumbs` (up to 4) and the detail page feeds it the case's own hats. **There is no case-photo feature at all**: no upload route, no uploader on the detail or edit pages. It was removed in two stages and that is worth knowing — the grid changed first while the detail page, the edit form and `POST /api/cases/{id}/photo` kept the feature alive, so a case with three hats rendered a screen-filling "NO PHOTO" box above its own contents. `tests/test_photos.py::test_there_is_no_case_photo_route` pins the removal. The vestigial `Case.photo_path` column is still there and unread — dropping it is destructive, so it is a decision rather than a side effect. It is no longer SERVED either: `CaseRead` dropped the field in 2.78 (it was published to every client and read by none), while `HatSummary.photo_path` — a hat's, not a case's — stays
- **Home carousel is two-up on desktop, one-up on mobile** — `lib/useMediaQuery.ts` (`useSyncExternalStore`, not `useState` + effect, which renders one frame at the wrong size and pops from one hat to two on every mount). The COUNT is decided in JS rather than by hiding a second slide in CSS, so a phone never downloads a photo it won't show — that's the whole reason this isn't a pure media query, and the tests exist to keep it that way. `visibleCount` is clamped to the number of hats WITH photos (a one-photo collection rendering the same hat twice reads as a bug), and the arrows hide when `length <= visibleCount` — stepping by a screenful through a 2-hat list lands back where it started, so the old `length > 1` guard left arrows that appeared to do nothing. jsdom has no `matchMedia`; `test/matchMedia.ts` installs a stub that answers "no match" by default (the mobile-first base case, so existing tests are unaffected) and `setViewportWidth()` opts a test into a width
- **Bottom nav vs the keyboard**: iOS positions `fixed` elements against the VISUAL viewport, so the nav rides up to mid-screen over whatever is focused. `lib/useKeyboardOpen.ts` (mounted once in AppShell) watches `visualViewport` — the only thing that reports this, since no `window` resize fires — and sets `body.hr-keyboard-open`, which hides the nav. Applies to every input; the earlier per-combobox fix missed plain `<select>`s
- **Build stamp**: `.dockerignore` excludes `.git` and the frontend stage only receives `frontend/`, so nothing in the image can learn the commit — `scripts/stamp-build.sh` writes `HEADROOM_BUILD_SHA` into the `.env` compose reads automatically, and `setup.sh` installs git hooks so a pull keeps it current
- **Free-text vocabulary**: `services/vocabulary.py` keeps `construction` and `artist_series` from splitting into five spellings of one thing. Two layers — `GET /api/meta/{constructions,collections}` suggests what's in use, and `canonicalize()` on write snaps a typed value to the spelling already on record (curated `KNOWN_CONSTRUCTIONS` checked first, since it's authoritative before any hat uses it). Folds case, whitespace AND accents ("Piña" = "Pina" = "PINA" — one drop typed with and without a long-press). `_preferred()` is the single tiebreak used by BOTH the write path and the merge: curated spelling → most accents (adding one is deliberate, dropping one is a slip) → most common → alphabetical. On write the value on record wins ties; the typed one only wins when it carries accents the stored one dropped. Matching is in Python, not SQL — SQLite's `lower()` is ASCII-only and would silently skip every accented row. `merge_case_variants()` repairs pre-existing variants, run once from lifespan behind `vocabulary_merged_v1`
- **Case capacity**: `services/capacity.py::evaluate` is the ONE rule — used by `hat_service._validate_capacity` to enforce it on write and by `routes/cases.case_to_read` to publish `accepts_*` / `free_*` / `overfull` / `nominal_capacity` for the picker. Two implementations would drift, and a picker that disagrees offers a case the save rejects with 409. Occupancy excludes disposed hats (they free their slot). **`frontend/src/lib/capacity.ts` is the one deliberate exception** and is not a second rule: it holds only the DEFAULT figures, for the create/edit placeholder — the one number no particular case can report, since a case publishes its own. It was hand-typed into two pages as "Default: 4 regular / 6 beanies" (wrong in both digits — 4 is the overfill limit, not nominal), which is why `tests/test_capacity_parity.py` now pins it to the Python **and** asserts the placeholder is interpolated rather than typed, since a hand-written string would pass the value check while still displaying the wrong numbers
- **Case picker**: `components/hats/CasePicker.tsx` — searchable, grouped by room, grays out cases that would 409 with the reason. Replaced a `<select>` that became a 60-row iOS picker wheel. Any dropdown-style picker must call `usePickerOpen`, which hides the fixed bottom nav while open (z-index 100, and iOS rides it up to mid-screen when the keyboard opens)
- **Beanie shapes are styles, and `is_beanie` has ONE definition.** melin names its beanie shapes like any other model (Journey, Destination, All Day — its own "Beanie Shape Guide"), so they are `HatStyle` members, not one bucket. `Hat.is_beanie` is a real column (search filters query it, capacity depends on it) **derived** from style, so `schemas/hat.BEANIE_STYLES` + `is_beanie_style()` are the single definition — same reasoning as `Hat.set_construction` owning hydro/hydrolite. A shape missing from the set packs 3-to-a-case instead of 6, vanishes from the Beanies filter, and makes the picker offer cases the save then 409s. `GET /api/meta/styles` **publishes `is_beanie` per option** rather than letting the frontend re-derive it: the flag decides which cases the picker offers, and a hardcoded TS list would be a second definition. `beanie` remains as "Beanie (unspecified)" — existing rows use it and an unidentified shape is a real state
- **Domain model**: Rooms contain Cases contain Hats — **and Rooms can contain Hats directly** (2.33). A hat kept on a shelf, a hook or a stand has `direct_room_id` and no case; `Hat.room` resolves either, so readers didn't change. The two are **mutually exclusive** — `assign_hat` clears one when it sets the other, because a cased hat's room IS its case's room. Any style may be room-stored (Caddies and Aviators don't fit a travel case at all, but nothing is restricted). Anything filtering hats by room must cover BOTH — `search_service._in_room()` is that disjunction, and `Hat.room_id` being a `@property` means it cannot appear in a `WHERE`; filtering only through the case silently excluded every room-stored hat while the client-side Hats filter kept showing them. `delete_room` moves caseless hats as well as cases. Cases are type-exclusive. **Full vs overfull are different states**: the default is 3 regular hats OR 6 beanies, and `OVERFILL_ALLOWANCE = 1` lets one more REGULAR hat in, accepted on write and reported as `overfull`. **Beanies get `BEANIE_OVERFILL_ALLOWANCE = 0`**: 3 is melin's *name* for the case ("3 Hat Travel Case") so a 4th demonstrably fitting was never a measurement, where 6 is the owner stating how many beanies belong in a case — a stated number is exact, the same way a per-case override is. **The beanie figure has moved twice (3 → 8 → 6)**, so it is never restated by hand: `services/capacity.py::MAX_BEANIE` is the value, `frontend/src/lib/capacity.ts::DEFAULT_BEANIE_CAPACITY` is the UI's copy of the *default* (the one number no particular case can report), and `tests/test_capacity_parity.py` fails if the two drift — the same parity mechanism `valuation.ts` uses. `CaseRead` serves `nominal_regular`/`nominal_beanie` so no client re-derives either. `free_*` counts down to NOMINAL and hits 0 at full, so the picker renders occupancy from `nominal_capacity`, never `used + free` — the latter shows a 4th hat in a 3-hat case as "4/4". The 409 quotes `limit_*`, not `max_*`. A per-case `capacity` override gets **no** allowance: the field exists for "a case you don't want to cram", so a stated number is exact. Exactly one room carries `is_default` — it's the fallback orphaned cases move to and the room new cases land in when none is named, so it's the only room that can't be deleted. Any room can take the role (`POST /api/rooms/{id}/default`), which frees the previous one for deletion; `database.ensure_default_room()` repairs the invariant on boot. Deliberately a flag, not a hardcoded `id=1`. Disposed hats stay in the DB but free their case slot
- **Hat photo pipeline**: Upload → Pillow resize/HEIC convert (JPEG, off the event loop — **retained as `original_path`**, the only thing a re-cut can work from) → `rembg` background removal (transparent PNG, becomes canonical) → 320px WebP thumbnail (`thumb_path`, what the grids render) → Claude Vision tool-use → eBay refresh (best-effort) → Melin resale → persist. Per-stage timing is logged (`hat=… rembg=…s claude=…s`), and the stage in progress is published to the hat row by `_publish_stage` through a SEPARATE session (`async_sessionmaker(bind=db.bind)`), so a reader sees `Cutting out…` while the pipeline's own transaction is still open. `POST /api/hats/{id}/recut` re-runs only the rembg half from the retained original — for a bill the model clipped — without spending a Claude call; `POST /api/hats/{id}/reanalyze` is the other half
- **Pipeline degradation**: Each step (bg-removal, Claude, eBay) can fail without breaking the others; failures land in `hat.analysis_status` (`ok` / `skipped` / `error` / `fallback`) with `analysis_error` text. eBay errors are logged but never block.
- **Analysis fallback**: When Claude is unconfigured OR errors, `run_fallback_analysis()` applies mask-derived colors (PNG canonical only — background rejected by construction) plus a Google Vision logo brand when that key exists → `analysis_status='fallback'`. Produces nothing → prior `skipped`/`error` state stands. Never sets model_name/price; eBay comps stay Claude-gated.
- **Bulk import**: `import_service.start_worker()` runs from lifespan. Items processed one-at-a-time. The worker loop survives ANY per-item exception (never dies). On boot, `_recover_on_boot()` re-queues items stranded in `processing`, recomputes counters, and closes jobs whose items are all terminal (e.g. all-oversize). Canceled jobs are never flipped back to `done`. The upload route caps per-file (chunked read) and total-batch bytes to bound RAM.
- **Activity log / audit**: `log_activity(db, kind=, entity_type=, entity_id=, summary=, details=)` is fire-and-forget; failures swallowed; **caller commits** (failed-login and other pre-exception paths must commit explicitly before raising). Covers auth events (login success/failed/blocked, password change, token rotation, passkey add/remove), backup downloads, key/cred changes, and share-link create/revoke. Daily prune task in lifespan.
- **Auth**: argon2id passwords verified/hashed OFF the event loop under a concurrency bound (`verify_password_async`/`hash_password_async`). Login rate-limited per (ip, username), in-memory, with empty-key cleanup. First-run `/api/auth/setup` is serialized against a concurrent second POST via an `app_settings` PK sentinel (`SETUP_SENTINEL_KEY`, no duplicate owners) — and a sentinel found with ZERO users is deleted first, because a sentinel outliving the row it guards was the bug behind the documented password-recovery recipe: `DELETE FROM users` then `/setup` answered "Setup already completed" forever, on an image with no `sqlite3` binary to fix it with. **Password change rotates the API token** as well as revoking other sessions (complete compromise response)
- **API key resolution**: `settings_service.get_anthropic_key()` checks DB first (UI-managed), then env (`HEADROOM_ANTHROPIC_API_KEY`). DB always wins. Same for `get_anthropic_model()` and eBay `get_creds()`. Set/clear via public `set_setting`/`get_setting`
- **API key safety**: Routes return only `ApiKeyStatus` (configured / source / masked prefix+suffix) — the raw key never goes back over the wire. Same for eBay creds
- **Readiness redaction**: `GET /health/ready` is unauthenticated (Docker healthcheck) — it returns booleans only for anonymous callers (no fs paths, key source, or raw error text); authenticated callers get full detail plus an import-worker liveness canary
- **Readiness gates on free space and worker liveness**, not just "is it writable". The old probe wrote two bytes, and two bytes fit on a volume with 8KB free while a 200MB tarball doesn't — `utils/disk.py` has two thresholds saying two different things (`low` = warn, `ok=False` = readiness fails below `HEADROOM_DISK_MIN_FREE_MB`, an absolute floor because what matters is whether the next backup fits, which is a size not a share). Worker liveness is gated on `worker_expected()` (the env flag) rather than `worker_alive()` alone — the latter is False for a *disabled* worker too, and the test suite runs with both off. Together these are the only reason the container can go unhealthy for the two failures most likely across weeks of unattended running; `restart: unless-stopped` was structurally blind to both. A broken measurement reports `ok=True` — a health signal that fails closed is worse than none
- **`add_middleware` PREPENDS**, so the LAST added is OUTERMOST. `SecurityHeadersMiddleware` must be added last or the auth gate's 401 short-circuits before reaching it — an anonymous `GET /api/hats` came back with two headers, no CSP, no nosniff, no X-Frame-Options, for two years. `BodySizeLimitMiddleware` (`limits.py`) sits outside even that: non-multipart bodies over `HEADROOM_MAX_BODY_BYTES` (2MB) are refused with 413 before the gate spends a DB lookup on them. Multipart is deliberately exempt — those routes stream to disk under their own much larger caps. Bytes are counted as well as `Content-Length` checked, since a chunked request declares nothing
- **Errors are durable**: `error_handler.log_unhandled` writes an `error.unhandled` activity row for every unhandled exception, then Starlette re-raises so the traceback still reaches the container log. It resolves the session through `request.app.state.session_factory` (the seam tests swap), not the module-level `async_session`. `validation_error` strips `input`/`ctx`/`url` from 422 bodies — pydantic puts the offending value in every error and FastAPI serializes it, so a password rejected as too short was echoed back in clear text. Note when testing: a route added AFTER `create_app` is shadowed by the SPA catch-all, so failure tests must break a real route
- **Secrets never go in a URL**: httpx logs the full request URL at INFO, so `?key=` put the Google Vision credential in the container log on every fallback analysis. It goes in `X-Goog-Api-Key` now
- **Disposition (soft delete)**: `dispose_hat()` sets `disposed_at` + 4 metadata columns. `_validate_capacity` and `_get_next_position` skip disposed hats. `undispose_hat()` restores AND **reassigns `position_in_case`** so it can't collide with a hat added while it was disposed. If the case is full it lands unassigned. Default `GET /api/hats` filters to `status=active`; `?status=disposed`/`?status=all` available
- **Wear log**: one row per hat per day; unique `(hat_id, worn_at)` constraint + IntegrityError-tolerant insert make the "wearing this today" tap idempotent even under a double-tap race
- **Search**: Multi-term AND across style/condition/size/colors/room/brand/model_name/artist_series/construction; disposed hats excluded. Default searches `general_color` (normalized to the palette via `normalize_hex_name` — at analysis time, at the one-time startup backfill flagged `color_names_normalized_v1`, AND on manual `PUT /api/hats/{id}/colors` edits); `exact_colors=true` searches `color_name`
- **Color terms match MAJOR colors by default** (`search_service.MAJOR_COLOR_RANK = 2`, `COLOR_SCOPES = major|accent|all`). Matching every swatch made color search useless here — every melin hat is a dark crown with a bright logo, so "pink" returned every black cap with a pink mark and the accent colors are precisely the ones that vary. Keyed on `dominance_rank`, not `tier`, for the same reason the similarity ranking is. **`dominance_rank` is assigned POSITIONALLY by every writer** (`enumerate(start=1)`), so a test that states a rank in the payload is silently ignored — build fixtures by order
- **`.card` declares `display: block`.** It is applied to an `<a>` in a dozen-odd places (deliberately not counted — the last count was written as "six" and was wrong within two releases), and an anchor is inline by default: `h-100` is ignored and the border breaks across line boxes. Invisible for years because every card was a `<div>`; it surfaced the moment 2.37 made the guest tiles links
- **A public search must only match fields the caller can SEE.** `search_hats(public_fields_only=True)` drops the `condition` / `size` / `artist_series` / `construction` clauses **and the hydro/hydrolite flags derived from construction**, because matching on a field the projection withholds turns search into an ORACLE for it — `?q=worn` returned exactly the worn hats, so a guest could read every hat's condition by probing. Guest search passes `limit=None` — no cap at all, where the owner's search takes `SEARCH_LIMIT` (50) — because the response reports its own length as the match count and a truncated list makes that count a lie (the `len()`-of-a-capped-list mistake, made three times now: colorway catalog, analysis `pending_count`, this). A `GUEST_SEARCH_LIMIT` of 500 stood in for "uncapped" until 2.78; `hat_count` on the guest collection is likewise the whole collection
- **Color-similarity search**: `GET /api/search/color?hex=` — **membership is CATEGORICAL, ranking is by distance.** It used to be a CIEDE2000 distance under a cutoff, tuned three times (30 → 22 → 26) and wrong every time. The measurement that settles it: within-family palette distances reach **ΔE 55.8** (light blue→navy, both plainly blue) while cross-family ones start at **15.4** (black→navy) — the ranges *invert*, so no threshold can keep the first and reject the second. At 26, **51 cross-family pairs matched** (black/navy, silver/beige, white/cream) and every search returned most of the shelf. `color_extraction.is_same_color()` now decides membership on the curated names via `families_of_lab()` (every palette entry within `FAMILY_AMBIGUITY_MARGIN = 5` of the nearest — a margin asking "is this classification ambiguous?", not "is this color close?"; saturated targets always resolve to exactly one family, only muted swatches come out ambiguous). `_COLOR_FAMILIES` maps a name to a SET, because charcoal is both a soft black and a dark grey and forcing it into one bucket makes the other search wrong. **Muted swatches fall back to HUE ANGLE, and **only ones DARKER than the target**: a dark teal is nearest *charcoal* by ΔE because ΔE is dominated by lightness, but its hue is 197°, identical to a mid teal's. The darker-only half is load-bearing and was missing until 2.58.0 — **chroma is bounded by lightness**, so at L=95 a low chroma is the most a color can have rather than evidence of desaturation, and the chroma RATIO against a mid-lightness target is then a comparison between two different ceilings. It passed silently: searching **olive returned the cream hats** (ΔE 40.0), plus olive→beige, tan→cream and gold→beige — the entire remaining cross-family leak, measured over the full palette cross-product. Only four palette entries sit inside the chroma window the fallback opens and they split exactly on lightness: navy (L=15) and dark brown (L=21) are what it is for, beige (L=83) and cream (L=95) are what leaked, with a 61-point gap between. Fixed with a structural question rather than a fourth tuned constant, which matters given the three cutoffs (30 → 22 → 26) that came before. `tests/test_find_the_hat.py` now asserts **zero cross-family matches over every ordered palette pair**, so this cannot regress quietly. That fallback is gated by the pre-existing chroma-ratio guard (`is_neutral_mismatch`) — a dark teal keeps 41% of teal's chroma, a blue-grey 20% of blue's, and their absolute chromas are 11.1 and 11.7, so nothing but the ratio separates them — and blue/purple is vetoed outright (`_INCOMPATIBLE_FAMILIES`) because CIELAB's hue angle is non-linear through the blue region. Distance now only ORDERS matches, with `_RANK_DISTANCE_BUDGET` (rank 1 unlimited — being the right color IS the question; rank 2 ≤ 18, deeper ≤ 12) so a pink brim still counts and a pinkish logo doesn't. `ColorSearchResult.distance` is the raw ΔE and is NOT the sort key; `matched_rank` explains why a Δ0 accent sits below a Δ5 primary. Palette chips from `GET /api/meta/colors`. **The stored NAME stays RGB-nearest (`nearest_color_name`) while search membership is CIEDE2000, and unifying them on ΔE was measured, not skipped**: over a 512-point RGB grid the two disagree on 39% of points, and the ΔE-nearest name is wrong where it matters — pure blue comes out "purple", the same non-linearity through the blue region that `_INCOMPATIBLE_FAMILIES` vetoes. Neither single-nearest metric names colors reliably; the classifier sidesteps it by keeping every candidate within a margin and reasoning about families. The docstring on `nearest_color_name` carries the numbers so nobody re-runs the experiment expecting a different answer
- **Certificate lifetime has a hard ceiling at 825 days, and it is Safari's.** `Caddyfile` (bind-mounted by the https-lan overlay) issues an **820d** leaf via `tls { issuer internal { lifetime 820d } }` plus `pki { ca local { intermediate_lifetime 3000d } }`. Caddy's default is **twelve hours**, which is a fine default until renewal stops — it did, an unclean shutdown ate the stored leaf key, and Caddy re-queued a renewal every ten minutes for **37 days** while serving the expired cert. **A Caddyfile rather than `caddy reverse-proxy` because the CLI cannot express PKI options at all**, so the default was not overridable in the old form. The numbers are not free choices: Safari (so every iPhone) rejects a server certificate whose validity exceeds **825 days** even under a manually installed root — the quoted 398-day cap is a *different* rule covering only Apple's PREINSTALLED roots — and **Chrome and Firefox impose no limit here**, so a 10-year cert works on the laptop you test from and fails on every phone with what looks like a trust-store error. The intermediate must clear `renewal_window_ratio` (1/3) × the leaf and stay under the 3600d root; `tests/test_tls_health.py` pins both, since the second surfaces only as a sidecar that won't start. **The ROOT is untouched by any of this** — changing `intermediate_lifetime` reissues the intermediate, which is presented during the handshake, not the self-signed anchor in each keychain, so no device reinstalls. `docker-compose.https.yml` keeps the CLI form deliberately: Let's Encrypt sets its own 90-day lifetime, so there is nothing to choose. The `Caddyfile` proxies to **`127.0.0.1:8000`, never `localhost`**: on a dual-stack host `localhost` resolves to `::1` first, uvicorn binds `0.0.0.0` (v4 only), and Caddy returned 502 on the refused v6 dial rather than retrying v4 — observed live as the nav badge's count request failing intermittently. **Shipping that config does NOT fix an existing install, and the failure is silent.** Caddy loads the intermediate it already has and only regenerates one when it is expiring, so every box that ran the overlay before 2.48 kept a **7-day** intermediate (the old default) and quietly logged `cert lifetime would exceed issuer NotAfter, clamping lifetime` — 820 days requested, ~6 granted, because a leaf cannot outlive its issuer. The real deployment ran that way for days. The repair is to delete the intermediate AND both issued leaves (they are signed by it, so replacing the issuer alone leaves a chain that does not build) then restart Caddy; **the root is untouched, so no device re-trusts**. `ca_vault.clamped_by_issuer()` detects it — a clamped leaf's expiry matches its issuer's to the second — because the two failures look identical on the certificate and have opposite fixes: renewal repairs an old leaf and can never repair a clamped one, and the Trust-this-device card used to advise the restart that loops
- **`.local` never crosses a VPN, and the failure presents as an outage.** mDNS is link-local **multicast**: no server holds the record, so `headroom.local` cannot resolve over Teleport/Tailscale/WireGuard or across a routed subnet, and there is no DNS anywhere to point at it. The IP is not a fallback for two compounding reasons — **Caddy rejects a TLS handshake whose SNI matches no configured site** (`curl --resolve headroom.local:443:<ip> https://headroom.local/` → 200 while `curl https://<ip>/` → **000**, no response, even with `-k`), and the certificate carries `DNS:headroom.local` with **no IP SAN**, so the name check would fail anyway. **The trap is Caddy's automatic HTTP→HTTPS redirect**: `http://<ip>/` answers **308 → `https://<ip>/`**, the one address that cannot complete a handshake, so the first thing anyone tries hands back the thing that is broken and the server reads as down. Fix: `Caddyfile`'s site line is `{$HEADROOM_SITE_ADDRESSES:headroom.local}` — comma-separated, defaulting to the mDNS name so existing installs are unchanged; listing the LAN IP makes Caddy serve it AND sign it into the cert as an IP SAN under **the same root**, so already-trusting devices need no reinstall. **Passkeys stay bound to `HEADROOM_ORIGIN`** — WebAuthn credentials are per-origin, so one registered at `https://headroom.local` is not offered at `https://<ip>`; that is WebAuthn working, not a misconfiguration, and no certificate change fixes it (password login works on both). The zero-config remote path is **`http://<ip>:8000`**, which is uvicorn direct and bypasses Caddy entirely — no secure context, so no passkeys there either
- **Share tokens are redacted wherever a path is written down**: `utils/redaction.py` owns the rule and three sinks use it — uvicorn's access-log filter (`app._RedactShareTokens`) and BOTH halves of `error_handler.log_unhandled` (the `error.unhandled` activity ROW and the logger line beside it). A share token is a 256-bit bearer credential and a PATH parameter, so `error_handler`'s stated mitigation — store `path`, never the full URL, "because query strings carry search terms and tokens" — misses its own worst case exactly. The DB row is the serious one: the database is what the scheduled backup uploads off the box, so an unredacted row puts a live token on a NAS or a cloud remote for as long as that archive is kept. The first version of this fix covered the access log only; two of the three sinks were left leaking by a change whose entire subject was the leak, which is the argument for one helper over a regex applied wherever the author was looking
- **Path traversal protection**: one shared implementation in `utils/paths.py` (`safe_join` / `safe_file`), not two copies. `_safe_spa_path()` is a thin wrapper over it defending the SPA fallback against `/%2e%2e/data/headroom.db`-class attacks; the share-photo streamer calls `safe_file` directly
- **URL-seeded filters**: the Cases type filter lives in the URL (`/cases?type=archive`, `replace: true` so tapping through filters doesn't build a back stack); `useHatFilters` and Search seed from query params (`?style=`, `?color=`, `?q=`) **once**, as initial state — the controls own it afterwards, since a two-way binding fights the user every time they widen a filter a link had set. `useHatFilters` also opens the filter bar when a link arrived with filters, so the reason the list is short is on screen
- **Query keys**: `['hats', 'disposed']` IS covered by `['hats']` — TanStack matches array keys by prefix element-wise, so `invalidateHatViews` refreshes it. (This entry claimed the opposite for a long time. The genuine sibling traps below are the ones where the shared text is not a whole element: `['room']` vs `['rooms']`, and `['admin','recent-errors']` vs `['admin','recent-errors-count']`.) What IS true of the disposed list is that Valuation and Stats need what has left the collection for realized totals, and it must never be summed with the active list. `['rooms']` for full `RoomRead[]`, `['room', id]` for one room's CONTENTS (a **sibling** of `['rooms']`, not covered by it — "rooms" is not a prefix of "room", so `invalidateHatViews` lists both), `['meta', 'rooms']` for dropdown options — invalidate all three on room mutations. **Anything that changes a hat's existence, disposition or case membership must go through `lib/invalidate.ts::invalidateHatViews`** — `['cases']` carries the occupancy counts, `['case', displayId]` the case's own hat list and `['rooms']` the per-room counts, and mutations that invalidated only `['hats']` left all three stale for the 30s `staleTime`. `['case']` is passed as a bare prefix so every mounted case detail is covered. `['settings', 'api-key']`, `['settings', 'google-vision-key']`, `['settings', 'model']`, `['settings', ## Conventions

- Routes in `src/headroom/routes/`, register in `routes/__init__.py`. **Order matters** when paths overlap — `/api/hats/import` must register before `/api/hats/{hat_id}` so the path parser doesn't shadow it
- `@pytest.mark.anyio` for async tests, asyncio backend only (no trio). Sync tests in this codebase need `pytestmark = pytest.mark.anyio` because the autouse `setup_db` fixture is async. The `anyio` marker comes from the `anyio` package's pytest plugin (no separate `pytest-anyio` dependency)
- Dev dependencies in `[dependency-groups] dev` in pyproject.toml
- **ruff enforces `PLC0415` (no imports inside functions) and `RUF100` (no unused `noqa`)**. The local-import idiom had spread to ~90 sites, and it is how late-binding seams break silently: a test patches `module.async_session` and a function importing `async_session` locally binds the REAL one at call time. Every remaining `# noqa: PLC0415` carries its reason in prose on the same line (an import cycle, a heavy optional dependency, a seam that must resolve at call time), and a seam that must follow a monkeypatch is written as a module-attribute call (`hat_analysis_pipeline.refresh_melin_resale(hat)`, `search_service.search_hats(...)`) rather than a `from … import`
- **Operator knobs reach the container only through `docker-compose.yml`'s `environment:` passthrough block** (`${VAR:-}` for each). A `.env` beside the compose file is INTERPOLATION for compose itself, not the container's environment — so `HEADROOM_SETUP_TOKEN`, `HEADROOM_REPRICING_*`, `HEADROOM_MDNS_HOSTNAME` and a dozen others documented as `.env` settings reached nothing for several releases (the mDNS hostname reached only Caddy, so the app advertised `headroom.local` while Caddy served `hats.local`). `tests/test_env_passthrough.py` parses the compose file and asserts every `HEADROOM_` name the code reads is forwarded. The empty-string default this produces is treated as UNSET everywhere: `Settings` sets `env_ignore_empty=True` and `env_flag`/`env_int`/`env_float` fall back on `""`, or `HEADROOM_SETUP_TOKEN=""` would have gated setup on a blank token
- **Wire-level contract tests**: `tests/test_api_contract.py` enumerates `app.openapi()` and asserts every operation declares a response schema (a route returning a bare dict is invisible to the TypeScript types), `tests/test_frontend_constants_parity.py` reads server constants the frontend restates (`STAGES`, `DEFAULT_HAT_BASICS`, `MAX_FILES`, the share-expiry seed) out of the TSX, and on the frontend `styles/classes.test.ts` (every class used in TSX is defined in `app.css` — ten Bootstrap-era classes were styled by nothing), `test/accessibleNames.test.ts` (every form control has a name) and `styles/tokens.test.ts` (every `var(--x)` is defined) are source scans, chosen over rendering because the property is static and rendering needs a mock per page
- Frontend API functions in `frontend/src/api/`, types in `frontend/src/types/`
- `datetime.now(timezone.utc)` over the deprecated `datetime.utcnow()`
- **JSX separators**: use the literal Unicode `·` in `<option>` labels, not the HTML entity `&middot;` — JSX renders entities inside expressions literally, so the entity shows up as raw text in the dropdown
- Dockerfile must run as a non-root `USER` (semgrep-enforced). **The rules are NOT in this repo** — `semgrep-cloud-platform/scan` is a check supplied by the Semgrep Cloud Platform GitHub App, alongside `security/snyk`, so grepping for a `.semgrep.yml` finds nothing and the scan runs anyway. It is **not a REQUIRED check**: `main` has no branch protection and no rulesets, so it reports and does not block. Both halves are worth stating — "semgrep-enforced" reads like a committed rule, and "required" reads like a gate. **Dependencies install from `requirements.txt`, the PROJECT from `uv sync --frozen`** — that split is a measured 490s of an 873s Pi rebuild. `pyproject.toml` carries the `version` field, so cutting a release used to bust the dependency layer (`uv sync` 237s) and the rembg model layer beneath it (149s) for a string that has nothing to do with dependencies; `requirements.txt` is `uv export --no-emit-project`, byte-identical across a version bump, so both now survive one. `--require-hashes` keeps the supply-chain guarantee `--frozen` gave. **The version-bearing copies must stay AFTER the dependency install** or the whole thing silently reverts — `tests/test_requirements_export.py` pins that ordering and fails on drift from `uv.lock`. Regenerate with `uv export --frozen --no-dev --no-emit-project --format requirements-txt -o requirements.txt` whenever dependencies change. **A Dependabot PR touching backend deps is a starting point, not a mergeable change** — it cannot see that `requirements.txt` is DERIVED, so it either bumps that file alone (a transitive like `websockets`, which `uv.lock` never moves for) or bumps both to *different* resolutions (observed: lock said `annotated-types 0.7.0`, the same PR's requirements.txt said `0.8.0`, and `cbor2` was in one and not the other). Never fix one by regenerating on its branch — in the second case that silently discards half the update. Take the whole thing on your own branch with `uv lock --upgrade` + the export above, and close the Dependabot PRs as superseded. There is deliberately no auto-regenerating workflow: it needs `pull_request_target` plus a checkout of the PR branch, which is the pwn-request pattern this repo's own semgrep scan rejects
- **Rules of Hooks**: every `useState` / `useMemo` / `useEffect` / `useQuery` must run on every render — never call hooks after an early `return`. Common bug source on pages with `if (isLoading) return <Spinner />` followed by a derived `useMemo`
- **Mobile bottom-nav layout**: `.bottom-nav` uses `display: flex` with `flex: 1 1 0` items. The `.d-lg-none` utility class **must not** force `display: initial` at mobile breakpoints — that overrides the flex and stacks tabs vertically
- **Dependency updates are automated**: `.github/dependabot.yml` opens weekly PRs for npm, uv, Docker base images (incl. the `COPY --from=` uv pin) and Actions, with a 7-day cooldown mirroring `[tool.uv] exclude-newer`. Minor/patch are grouped into one PR; majors come individually. `.github/workflows/ci.yml` runs pytest + typecheck + production build + a real Docker build & health check on every PR, so those bumps verify themselves.
- **Releasing**: bump `pyproject.toml` AND `frontend/package.json` together, run `uv lock`, refresh `frontend/package-lock.json` (`npm install --package-lock-only`), regenerate `requirements.txt` if dependencies changed, and add a `CHANGELOG.md` entry (Keep-a-Changelog; a **Breaking** section justifies a major bump — e.g. build-arg renames, `--frozen`, auth behavior changes). Vite bakes the package.json version into the bundle as `__APP_VERSION__`. Cut the release with a `vX.Y.Z` git tag + `gh release create` (2.0.0 onward)
- **Merging/tagging from a worktree**: `main` is checked out by the primary clone, so anything that wants to switch to it locally fails with `fatal: 'main' is already used by worktree`. In particular `gh pr merge --delete-branch` **merges on the server first and only then fails** on cleanup — the error looks like the merge didn't happen when it did, so check `gh pr view <n> --json state` before retrying. Do the cleanup without a checkout instead: `gh pr merge <n> --squash`, then `git push origin --delete <branch>`. Tag by SHA rather than by branch — `git tag -a vX.Y.Z <merge-sha>` — since `git tag` on a branch you can't check out is the same trap
- **Env vars of note**: `HEADROOM_MDNS_ENABLED`/`_HOSTNAME`/`_PORT`/`_INTERFACE` (LAN discovery; `_INTERFACE` pins the zeroconf bind interface — defaults to the detected LAN IP so a Docker host-net container doesn't leak the responder onto docker0/veth, `all` restores all-interfaces), `HEADROOM_BUILD_SHA` (footer build stamp / Docker build-arg), `HEADROOM_BACKUP_*` (incl. `_KEEP`, a count — see `backup_service`; `_INCLUDE_CA`, default true, puts Caddy's CA **private keys** in the archive — see `ca_vault`), `HEADROOM_MAX_BODY_BYTES` (2MB, non-multipart only), `HEADROOM_DISK_MIN_FREE_MB`/`_WARN_PCT` (readiness floor / log warning), `HEADROOM_IMPORT_WORKER_ENABLED`, `HEADROOM_ANALYSIS_WORKER_ENABLED`, `HEADROOM_REPRICING_ENABLED`/`_INTERVAL_HOURS` (24)/`_DELAY_SECONDS` (1, spacing between sequential calls to somebody else's public API)/`_BATCH_LIMIT` (0 = uncapped), `HEADROOM_REMBG_CONCURRENCY` (concurrent rembg inferences, default **1** — both workers reach `remove_background` and a 179MB model plus a full-res decode is the app's largest allocation), `HEADROOM_MEM_LIMIT` (container memory ceiling, default 1g), `HEADROOM_REMBG_MODEL` (default `isnet-general-use` — `u2netp` is faster but cuts hat bills off), `HEADROOM_RP_ID`/`HEADROOM_ORIGIN` (passkeys), `HEADROOM_SETUP_TOKEN` (gates first-run setup when set; unset changes nothing). The retired `HEADROOM_ADMIN_TOKEN` is ignored
