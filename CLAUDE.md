# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is tracked in git (was previously local-only and drifted stale) — keep it current when you change architecture, add a service/route, or ship a release.

## Commands

- `./scripts/setup.sh` — Full setup: installs missing deps (uv, Node — accepts 22.22+ (react-router 8's engines floor, the highest of any dep; Node 20 is EOL), installs 26 fresh to match the image, and tries to upgrade npm to 12 to match the image's `ARG NPM_VERSION`, and now VERIFIES it took — on a Homebrew node the formula owns the `npm` symlink so a global upgrade is reverted by the next `brew upgrade node`, which the script now says outright rather than telling you to retry a command that cannot stick. Cosmetic for Docker deploys: the image installs its own pinned npm, Docker engine sans Desktop — colima/brew on macOS, get.docker.com on Linux), syncs backend+frontend, inits DB, builds SPA. Flags: `--docker-only` (just the engine, for the compose path), `--no-docker`, `--skip-build`
- `uv run uvicorn headroom.app:app --reload` — Run backend dev server (port 8000)
- `cd frontend && npm run dev` — Run frontend dev server (port 5173, proxies to backend)
- `cd frontend && npx vite build` — Production SPA build (output: `frontend/dist`, served by backend in prod)
- `cd frontend && npx tsc -b --noEmit` — TypeScript type-check (covers `*.test.tsx` too — they live under `src/`)
- `cd frontend && npm test` — Frontend unit tests (Vitest + Testing Library, jsdom). `npm run test:watch` to iterate
- `uv run pytest` — Run all tests (must run from project root)
- `uv run pytest tests/test_disposition.py::test_dispose_sets_fields` — Run single test
- `docker compose up -d --build` — Run as a Docker container (Pi-friendly)
- `docker compose -f docker-compose.yml -f docker-compose.mdns.yml up -d --build` — add LAN discovery (`headroom.local:8000`; host networking, Linux/Pi)
- `docker compose -f docker-compose.yml -f docker-compose.http80.yml up -d --build` — plain HTTP on port 80 via a Caddy sidecar (`http://headroom.local`, no TLS; password login only)
- `docker compose -f docker-compose.yml -f docker-compose.https-lan.yml up -d --build` — LAN HTTPS via Caddy's internal CA, so passkeys/Face ID work on `https://headroom.local`
- `HEADROOM_DOMAIN=hats.example.com docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build` — internet-facing HTTPS (Let's Encrypt)

## Architecture

**Backend** (Python 3.12+ — `.python-version` pins 3.14 locally to match the Docker image; FastAPI, SQLAlchemy async + aiosqlite):
- `src/headroom/app.py` — App factory: lifespan (single-process guard + init_db + branding seed + one-time vocabulary merge and color normalization + scheduled-backup task + activity-log/session prune task + bulk-import worker + **analysis worker** + thumbnail backfill + mDNS advertise), CORS, SPA serving with path-traversal protection
- `src/headroom/auth.py` — `SecurityHeadersMiddleware` (owns the app-wide CSP — including the `style-src 'self'` that once blocked a Google Fonts import) + `AuthGateMiddleware` (protects all `/api/*` + `/uploads/*`; open: `/api/auth/*`, `/api/public/*`, `/health*`, SPA shell/assets; `POST /share` share-target needs auth, `GET /share/<token>` is the public share SPA page) + `resolve_user()` (public — `/health/ready` uses it to decide how much detail to expose) + `require_user` dependency (`require_admin` is an alias — single role, every authenticated principal is fully privileged). Middleware resolves users via `app.state.session_factory` — tests swap it for the test DB
- `src/headroom/routes/` — `health`, `public` (unauthenticated branding logo for the login page), `auth` (setup/login/logout/me/token/passkeys), `cases`, `hats`, `import_jobs`, `rooms`, `search`, `meta`, `settings`, `admin`, `share`, `share_links` (mgmt + `/api/public/share/{token}` read-only view with token-gated photo streaming), `guest` (`/api/public/guest/*` — unauthenticated read-only browse+search, 404 when disabled), `ca_cert` (`GET /api/public/ca-certificate` — Caddy's ROOT cert so a device can trust `headroom.local`; **the filename is hardcoded and the handler takes no parameters**, because the same directory holds `root.key` and `intermediate.key`. Served as `application/x-x509-ca-cert` or iOS displays it instead of offering the install. **It reads `/caddy-ca/root.crt`, copied out of Caddy's PKI by the overlay's `caddy-ca-export` sidecar — NOT the PKI itself.** Mounting the PKI is what it did until 2.45 and it never worked on any install: Caddy creates that tree `0700 root`, the app container is non-root by policy, and `Path.is_file()` reports the failed traversal as plain `False` — so "mounted but unreadable" was indistinguishable from "not installed" and the 404 confidently told operators to check an overlay that was demonstrably already running. `_unavailable_detail()` now separates the two, and copying one public file out means this container has no key material in view at all. **The intermediate is the trap**: it sits beside the root, installs without error and achieves nothing, since a trust anchor is self-signed and installed out of band while an intermediate is presented during the handshake). `admin` is a **package** (`routes/admin/`) — `errors`, `backups`, `activity`, `reports`, `ebay`, `catalog`, `analysis` (queue status + bulk re-analyze), each a prefix-less router; `__init__.py` applies the `/api/admin` prefix, tag and `require_admin` once, so a submodule can't ship an unguarded admin route
- `src/headroom/models/` — `ActivityLog`, `AnalysisJob`, `AppSetting`, `AuthSession`, `Case`, `ColorwayEntry`, `Hat`, `HatColor`, `ImportJob`, `ImportJobItem`, `PasskeyCredential`, `Purchase`, `Room`, `ShareLink`, `User`, `WearLog`
- `src/headroom/services/`
  - `claude_analysis.py` — Claude Vision tool-use call → structured `HatAnalysis`. `_owner_context()` carries the owner's stated facts AND `_known_series_context()`, the collab/artist-series names already in the collection. Those are sent because **a series is rarely legible in a photo** (a woven label, an embroidery style), so an analyzer recalling them unaided misses most of them. Framed as a record of what the collection contains, **not** a menu — a candidate list invites a forced choice and a wrong series is indistinguishable from a right one, so the prompt says `null` beats a wrong match. Truncation past `MAX_KNOWN_SERIES` is stated in the prompt, never silent
  - `background_removal.py` — `rembg` (ONNX) → transparent PNG
  - `melin_recap.py` — Melin resale: deep links + live median asking price via the Sharetribe Flex public API (melinrecap is a Treet marketplace; anonymous public-read token, client id in config, `query_listings` is the test seam). Degrades to link-only on API failure.
  - `catalog_service.py` — Colorway catalog harvested from melinrecap listing titles ("Model - Colorway", `parse_listing_title`); purchase-history import + hat matching (sets hat.colorway/purchase_price/purchased_at). **The harvest isolates each category**: `query_listings` raises on any non-200, and one 429 used to abandon every category after it — sequential sweep, commits per page, endpoint already returned 202, so the result was a *silently* partial catalog indistinguishable from a complete one. `_fetch_page` retries with backoff; a category that still fails is recorded in `failed_categories` and the sweep continues. **`GET /api/admin/colorways/status` reports what is actually in the catalog** — the Settings card used to show `len(GET /api/meta/colorways)`, which is the AUTOCOMPLETE feed capped at `catalog_options`' default `limit=25`, so it read "25 models known" no matter how much had been harvested. `_units_to_add` is the single dedupe decision shared by import and preview. Endpoints: POST /api/admin/colorways/refresh, GET /api/admin/colorways/status, /api/admin/purchases/{import,match} (both take `?dry_run=true`), /api/admin/purchases/{id}/unmatch + /purchases/unmatch-all, GET /api/meta/colorways (autocomplete). **Unmatch is the undo matching never had** — it mutates hats and only reconsiders purchases with a NULL hat_id, so a wrong link was permanent and invisible (the hat still got *a* price and *a* colorway). `_revert_hat_fields` clears a field only when it still holds the value match wrote; anything edited since is somebody's deliberate value. `unmatch-all` keeps the purchase rows — re-importing years of orders is the expensive part. Route order matters: `unmatch-all` registers BEFORE `{purchase_id}`. **Matching is scored, not first-hit** (`_match_score`): size outranks colorway, a stated field that disagrees rules a hat out, ties are reported not guessed. **The MODEL is the gate and only the model** — a hat matches on exact token equality (`MODEL_EXACT`) or when its tokens are a **subset** of the purchase's (`MODEL_CONTAINED`, scored far lower), because `model_name` comes from Claude reading a PHOTO, which cannot show the sub-line, so it lands on the family (`odysea hydro`) while the receipt states the product (`Odysea Packable Hydro`). Asymmetric on purpose: a hat named *more* specifically than the receipt does not match, or one generic line claims any specific hat in the family. Everything else SCORES — owner-stated `artist_series`/`construction` (compared against the WHOLE title, since melin puts the series in either half: `Trenches Links Hydro` vs `Trenches Icon Hydro - Camo`) and the analyzer's color words against the receipt's colorway. Bonuses, never vetoes: 102 hats have no series and absence is not disagreement; putting them in the *gate* was tried and measured **worse** (143 → 105). **`_by_scarcity` — most-constrained purchase first — is worth more than any scoring change**, because assignment is greedy and in file order a line with fifty candidates takes the one hat the next line's only candidate was; it is keyed on `id(p)` not `p.id` since `preview_import` scores TRANSIENT rows whose PK is still None, and **both callers share it** or the preview under-reports the matches the import makes. On the real 294-unit history this is 41 → **144** matched, which is the **maximum bipartite matching _under the current gate_** — `test_matching_achieves_the_maximum_possible` proves it with a second, independent Kuhn's-algorithm implementation and is sabotage-checked (removing `_by_scarcity` fails it), so scoring/ordering changes cannot improve the result. **"Optimal" is relative to which pairs are eligible**: a hat with no `model_name` is structurally unmatchable and the superset direction is refused, so loosening either adds edges and could raise the ceiling — the stated target was 90% and this reaches 68%, the gap being contention (73 `Trenches Icon Hydro` purchases, 36 such hats) plus that deliberate strictness. **`preview_import` previews the whole CLICK, not the file** — importing runs `match_purchases_to_hats` over EVERY null-`hat_id` purchase, so a preview built from the file alone described a different operation: on the real collection it reported "1 to import, 0 would match" and the import then wrote **144 hat prices**. It now matches the file's lines together with the existing backlog and reports `would_match` / `would_match_backlog` / `would_match_total` separately, because the backlog is the part nobody asked for and the part that writes prices. `_matchable_hats` is the one query both paths use; `_model_tokens` is `lru_cache`d because matching is quadratic and scored twice per pair. **Import writes one row per UNIT** — a "× 2" line is two hats and a purchase matches one hat, so one row per line left the second hat of every multi-buy unpriced (~40% of lines in a real order history). Dedupe therefore counts rows rather than testing existence, keyed on (order_ref, item_title, price, **size**) — one real order bought the same model at the same price in Classic ×2 and Small ×1, and a key without size collapsed the Small. Both the importer and `preview_import` share `_line_fields` and an in-batch `staged` tally so the preview predicts the import exactly.
  - `ebay_service.py` — Browse API OAuth + comparable-listings stats. Refreshed automatically post-Claude.
  - `color_extraction.py` — Fallback dominant colors from the rembg cutout's alpha mask (hat pixels only, Pillow median-cut, curated ~25-name palette). No network. Also `normalize_hex_name()` (snap a hex to the palette) and the LAB ΔE color-similarity ranking.
  - `google_vision.py` — Fallback brand via Google Vision LOGO_DETECTION (REST + API key, no SDK). Key resolution DB > env like the others.
  - `hat_analysis_pipeline.py` — Orchestrates upload → bg-removal → Claude → eBay refresh → DB writes. `finalize_hat_photo()` (upload) and `reanalyze_existing_photo()` (reanalyze route, no bg-removal) share the key-check → Claude → apply → eBay → resale choreography; `analyze_hat_image` is patched here in tests (single seam).
  - `settings_service.py` — API-key + model + eBay-creds get/set/clear (DB > env precedence). Public `get_setting` / `set_setting`. Each external key provider is one frozen `KeyProvider` dataclass (`ANTHROPIC_KEY`, `GOOGLE_VISION_KEY`) driving both the generic `get_key`/`set_key`/`clear_key` **and** the generated HTTP routes — adding a provider is one entry plus one line in the `_mount_key_routes` loop.
  - `activity_service.py` — Append-only audit log; `log_activity()` is fire-and-forget. Daily retention prune.
  - `analysis_queue.py` — Single asyncio worker draining a queue of hat IDs so `POST /api/hats/{id}/photo` returns immediately instead of blocking for minutes on rembg+Claude. Hat wears `analysis_status='pending'` until the worker finishes; boot sweep re-queues hats stranded by a crash; `enqueue()` returning False makes the route run inline so work is never dropped. Env-gated `HEADROOM_ANALYSIS_WORKER_ENABLED`
  - `import_service.py` — Single asyncio worker draining a queue of bulk-import items. Survives restart AND per-item exceptions; boot sweep heals crash-stranded state (see Key Patterns).
  - `backup_service.py` — Streamed on-demand `tar.gz` + scheduled rolling backups to `/data/backups/`. **Written only when the data has actually changed**, and retention is a **COUNT** (`backup_keep()` → `HEADROOM_BACKUP_KEEP`, default 5; the old `HEADROOM_BACKUP_RETENTION_DAYS` is still read, as a count, so an existing `.env` keeps meaning something). Those two go together: age-based pruning plus change-gating has a steady state of **zero backups** on an idle system, because the last one ages out with nothing written to replace it. Counting can't do that. `_data_fingerprint_sync()` is size+mtime over the DB, **its `-wal` sidecar** (a WAL-mode commit can leave the main file untouched, so watching it alone calls a day of edits "no changes") and every file under uploads; `_fingerprint_path()` is a file in `backups/` and **must never move into `app_settings`** — the DB is part of what it measures, so storing it there would invalidate the cache every time it was written. A skipped cycle calls `record_skipped()`, which advances `last_attempt_at` (an idle scheduler must not look like a dead one) without clearing a standing failure. Skips the startup backup when a recent one exists. The scheduled loop survives any failure short of cancellation and records `BackupHealth` (last attempt/success, consecutive failures) at `GET /api/admin/backups/health`, because the file list can't distinguish a scheduler that died weeks ago from one that ran minutes ago. The loop CHECKS the return: `write_scheduled_backup` swallows its own exception and returns `None`, so calling `record_success()` unconditionally (as it did until 2.26) reported a backup failing every cycle as healthy. `record_failure` therefore takes a plain string as well as an exception, because that is the shape the likeliest failure arrives in. A raw-file fallback backup carries a `DEGRADED-BACKUP-README.txt` inside the archive. Optional off-box upload after each scheduled backup via `HEADROOM_BACKUP_UPLOAD_CMD` (`{path}`/`{dir}`/`{name}` substituted, argv/no-shell, best-effort/non-fatal, `_run_upload_hook`); `docker-compose.backup-rclone.yml` wires it to rclone (Box/S3/B2/…). **UI-configurable via `UPLOAD_PROVIDERS`** — one frozen `UploadProvider` per transport (rclone / rsync-over-SSH / Synology rsync daemon) driving the argv template, the destination regex, the card's setup steps and the `shutil.which` preflight, so adding one is a single entry rather than four edits that can disagree. The browser never sends a command: it sends a provider name and a destination that lands in exactly ONE argv slot. **Per-provider destination patterns are load-bearing** — `host:/path` is rsync over SSH, `host::module/path` is a DAEMON on port 873 whose first segment is a module name; one pattern for both would let a typo switch transport silently and fail with credentials nobody configured, looking like a broken NAS. `HEADROOM_BACKUP_RSYNC_PASSWORD` → `RSYNC_PASSWORD` via `upload_env()`, read from the host and never stored or returned (daemon mode only — rsync ignores it over SSH, which is why the SSH provider carries no secret rather than one that looks set and does nothing). `rsync`+`openssh-client` are IN the image (~3MB); rclone (~50MB) stays a bind mount.
  - `tls_health.py` — **Does the HTTPS front door serve a certificate a browser will accept?** Written after the real deployment served one that had expired **37 days** earlier with every other signal green: Caddy's stored leaf key vanished, so renewal queued every ten minutes and never completed. It opens a TLS connection to `HEADROOM_ORIGIN` and reads the SERVED chain — **not** Caddy's storage, because those disagree (that failure had a valid cert on disk and an expired one in Caddy's memory). `verify_mode = CERT_NONE` is load-bearing and is not the usual mistake: a verifying handshake fails on exactly the certificates this exists to report on. No request is written and nothing becomes trusted — the socket exists to capture the peer cert and close. **Reported, never enforced** — the cert belongs to Caddy, so failing readiness would restart-loop the app without fixing anything. `ca_fingerprint()` publishes the served root's SHA-256 because **Caddy names every root `Caddy Local Authority - <year> ECC Root`**, so two installs give two DIFFERENT roots with the SAME name; a browser matching by name reports "invalid signature" on a chain that verifies fine at the server, and nothing but the fingerprint separates them. `RENEWAL_GRACE_DAYS` is **30**, tuned to the 820-day leaf the `Caddyfile` now issues — it was 2, which was generous against a twelve-hour certificate and against an 820-day one is a fire alarm that rings as the roof falls in. Anything reading it as "expires within hours" (the Trust-this-device card once did) is copy left over from the old lifetime
  - `ca_vault.py` — **Caddy's local CA: keeping it, and noticing when it changes.** The 37-day outage cost a leaf key, which Caddy simply reissues. The **root** is the expensive one: every device installed it BY HAND through iOS Settings / macOS Keychain, and a root is self-signed, so nothing can vouch for a replacement — losing it means visiting every device. It lived only in Caddy's volume and was in **no backup this app takes**. The export sidecar now copies the whole authority to `/caddy-ca/pki` (**0700, uid 1000**, beside the 0644 `root.crt` that `routes/ca_cert` serves — two destinations, deliberately different modes) and `backup_service._add_ca_to_tar` folds it into the archive under `data/caddy-pki/` with a README, because the tarball gets uploaded to a NAS and by then nothing else says a trusted root's private key is inside it. `PKI_FILES` is **explicit, never globbed** — these are private keys, so what leaves the box is an inspected decision. `fingerprint_parts()` puts the CA in the backup change-gate, or a regenerated authority wouldn't trigger a backup and the archive holding the OLD root would age out while the new one was never captured, losing both. `check_root()` records the served fingerprint on first sight and reports a mismatch forever after — **it deliberately never self-heals**, since overwriting on mismatch would silence the alarm on the next poll while every device stayed broken. Surfaced as `TlsStatusRead.ca_changed`/`ca_expected_sha256`, which come from the ROUTE not `check_certificate` (answering them needs the DB; the dataclass is built by a sync network call) — `tests/test_tls_health.py` pins that asymmetry in both directions. `HEADROOM_BACKUP_INCLUDE_CA=false` opts out: a trusted root's key can sign for **any** host, which is broader than anything else in the archive. **Durability itself is not ours** — Caddy decides when to fsync, so a durable COPY is the only mitigation available
  - `mdns_service.py` — Advertises `headroom.local` on the LAN (python-zeroconf, best-effort, env-gated `HEADROOM_MDNS_*`). Registered as a background task off the boot path; Docker bridge blocks multicast so the `docker-compose.mdns.yml` overlay (host networking) is required to reach the LAN. Read-only status at `GET /api/settings/mdns`.
  - `valuation.py` — The server's copy of the valuation rule, for the one thing that can't import TypeScript: the inventory report. `frontend/src/lib/valuation.ts` is authoritative; `tests/test_valuation_parity.py` reads the constants out of the TS file and fails if the two drift (three hand-written copies drifting is what this replaced).
  - `export_service.py` — The collection as a downloadable **zip** (`index.html` + `images/`), for showing someone the collection when they cannot reach the app — `headroom.local` resolves for nobody off the LAN, which is why share links never worked in practice. A zip rather than one base64-embedded file: self-contained HTML is neat until it's 8MB of base64 no mail client will preview. Deliberately a SHOWCASE, not `report_service`'s valuation table — prices are opt-in (`include_values`, default off), matching the share-link projection. Images are re-encoded to **800px WebP q82** from the canonical photo (`utils/photo.make_export_image`), not copied from the 320px grid thumbnail — that looked soft the moment anyone opened the zip on a laptop, and upscaling it would be a bigger file that looks the same. **WebP**, which is open and royalty-free (not proprietary) and supported since Safari 14 / 2020. Measured against the alternatives on photographic cutouts: PNG lossless 137KB, PNG 256-color 26KB (softens the anti-aliased edge), JPEG 31KB but **no alpha at all** so the hats stop floating, WebP 9KB. AVIF is 13.5KB vs WebP's 13.9 — a few percent on real photos, not the ~30% it manages on flat synthetic images — so it buys nothing worth a Safari 16.4 floor. Derivatives are cached under `uploads/hats/export/`, keyed on the source filename and invalidated by mtime (a re-cut regenerates itself). **`utils/photo.export_derivative_path` is the one definition of where that file lives**, because two callers must agree: the export writes it and `POST /api/hats/{id}/photo` deletes it. It is the only derivative not named by a Hat column, so the replacement path's loop over `photo_path`/`original_path`/`thumb_path` silently missed it and every re-shot hat leaked an 800px WebP; **derivatives are written by `finalize_hat_photo` when the photo is processed**, backfilled at boot by `hat_service.backfill_export_images`, and anything left resolves in ONE `asyncio.to_thread` (`_resolve_images`) — the export used to generate them inline in the card loop, on the event loop, which is minutes of an app answering nothing plus a full-res decode resident beside rembg's model in a 1g container, and looked from outside like a download that did nothing. Named by hat **id** (an unassigned hat has no display_id, and two hats can briefly share one mid-reshuffle)
  - `retail_pricing.py` — **melin retail is LOOKED UP, not guessed.** `estimated_new_price` used to come entirely from Claude Vision, steered by price "anchors" in `SYSTEM_PROMPT` — and a photo cannot show a price, so those anchors WERE the answer. They said "HYDRO caps — $69 is the common price" long after the band had moved, so the whole collection (and valuation's retail fallback) was priced by a stale comment. The table is cross-checked against real order lines: **HYDRO $79, HYDROLite $99, beanie $79 (Journey + Destination), Aviator floor $99, case $49**. **`all_day` is deliberately absent**: it appears once, at $0.00, as the "FREE All Day Pom Beanie With Purchase" promo, and a giveaway is not a retail price — inheriting the beanie $79 would assert a number for the one beanie there is no evidence for. HYDROLite is matched BEFORE hydro (substring). `resolve_retail` order: a **Manual** price wins outright (same protection `resale_price_scope == "manual"` has), then the table, then Claude — but the table never pulls a *higher* estimate down, because the base is what a PLAIN example costs and collabs/Mill straw ($99–$180)/Thermal Aviators ($139–$179) legitimately exceed it. `base_retail` returning **None is a real answer**: Thermal is $79/$89/$99 on caps and $139/$179 on Aviators, so any single number would be invented. `backfill_retail_prices` repairs existing rows once from lifespan behind `retail_prices_v2` — fixing the code alone would leave the price depending on *when* a hat was photographed. `CASE_RETAIL` is published as `CaseRead.retail_price`, not stored per row (40 copies of one number waiting to disagree). **`lib/valuation.valueCases()` sums that SERVED price** — it was published and read by nothing until 2.34, so every total excluded the cases entirely. Kept as its own line, never folded into the hat figures: a case is valued at replacement cost where a hat is valued at market, and adding the two silently would make retention, unrealised gain and cost-per-hat all wrong invisibly
  - `tag_service.py` — **Physical tags: QR stickers and NFC are one feature.** Both carry a single URL, so this module owns its shape and nobody else builds one. **A hat tag keys on the immutable `hat.id`; a case tag keys on `display_id`.** That asymmetry is the whole design: a hat's `display_id` is derived from case + position, so it changes when the hat is reshuffled and is `None` while unassigned — which is exactly when you're tagging it. A sticker cannot be rewritten, so a display-id label would keep scanning and silently open a *different* hat. A case's `display_id` is painted on the case and never moves. Tags point at **`/t/h/{id}` / `/t/c/{display_id}`**, not at the real page — one indirection that costs nothing now and cannot be retrofitted once forty stickers exist. The **host is configurable** (`tag_base_url` app-setting, `GET/PUT/DELETE /api/settings/tags`), defaulting to the request origin: browse to the Pi by IP once and every tag written that afternoon names a DHCP lease. A base without an `http(s)` scheme is **rejected** — an NDEF URI record needs one and a bare `headroom.local:8000` QR is read as plain text, so it looks right and does nothing
  - `report_service.py` — Server-side HTML inventory report (browser Print → Save as PDF). Values hats via `valuation.value_hat`, not its own ranking.
  - `guest_view_service.py` — **unauthenticated read-only browsing, OFF by default** (`guest_view_enabled` app-setting). Routes live in `routes/guest.py` under `/api/public/guest/`, and **404 rather than 403 when disabled** — a 403 confirms the feature exists on a private install. Reuses the share-link `SharedHat` projection rather than a second one (no prices/purchases/disposition/wear/analysis/notes; a second projection is a second thing to keep in step, and the one that fell behind would be the one exposed to strangers) and delegates search to `search_service` for the same reason. `AuthStatus.guest_view_enabled` tells the login screen whether to show the link — carried on the one unauthenticated call that page already makes
  - `auth_service.py` (argon2 + sessions + rate limiting), `share_link_service.py`, `analysis_job_service.py` (backs `/api/admin/analysis/*`; **`ids_for_reanalysis` covers EVERY hat with a photo** — disposed is the only exclusion. An `only_priced_by_claude` filter used to sit here behind a default-ON checkbox labelled "Leave hand-entered prices alone"; it was redundant (a Manual price is protected by `resolve_retail` and the two `resale_price_scope == "manual"` guards) and after 2.27 moved most hats to `melin retail` it silently cut a 234-hat run to 45. **`pending_count` is a SQL `COUNT`, never `len()` of the 50-row preview list**), `case_service.py`, `hat_service.py`, `room_service.py`, `search_service.py`, `label_service.py` (QR label sheets for cases AND hats — occupancy comes from `capacity.evaluate`, never a local copy), `passkey_service.py` (WebAuthn ceremonies)
- `src/headroom/routes/share.py` — Web Share Target endpoint (`POST /share`). Receives multipart photos shared from the system share sheet (Android Chrome PWA), creates an import job, 303-redirects to `/hats/import?job=N`. iOS uses an iOS Shortcut against `/api/hats/import` instead — see Settings page recipe.

## Key Patterns

- **Async relationship loading**: Always use `selectinload()` for relationships; after commit + relationship changes, call `db.expire_all()` then re-query (see `_reload_hat()`, `_reload_case()`). `expire_all()` is **synchronous** on `AsyncSession` (no `await`), and `run_sync()` takes a **sync** callable — passing an `async def` fails at runtime, not at import
- **Database migrations**: `database.py:_run_migrations()` runs `ALTER TABLE` against existing DBs using **fully-static** DDL strings (no f-string interpolation into `text()`); `_HAT_COLUMN_DDL` is the source of truth for hat-column additions. `tests/test_schema_consistency.py` enforces that EVERY `Hat` model column is covered by the DDL (a forgotten entry bricks every hat read on an upgraded DB). New tables (activity_log, import_jobs, import_job_items, wear_log) are picked up by `Base.metadata.create_all`
- **`logo_detected`** records what the analyzer SAW (mark + owning brand); `brand` may be inferred. Set by Claude (tool-schema field, required, null allowed) and by the Google Vision fallback.
- **Analysis-written free text is canonicalised too.** `vocabulary.canonicalize` ran only in `hat_service` (the client PUT/POST path); the ANALYSIS path wrote straight through, so Claude returning `skye walker` created a second entry beside the owner's `Skye Walker`. Invisible by construction — both hats have *a* series, and the split shows only as near-duplicate rows in the autocomplete, the Stats collab chart and the filters. `hat_analysis_pipeline._canonicalize_analysis_text()` runs after `_apply_analysis` on BOTH call sites and covers `artist_series` plus a construction Claude filled in; construction goes through `set_construction` so the derived flags can't drift
- **Owner-stated facts are sent to Claude as ground truth**: `claude_analysis._owner_context()` builds the prompt sentence from `selected_style` AND `selected_construction`. Protecting the stored value is not enough — before 2.17 the construction was never sent, so a hat recorded as Thermal came back with `model_name='A-Game HYDROLite'`: right field, wrong name in the one a person reads. `_strip_contradicting_construction()` also removes a rival construction from `model_name` on every analysis, so a full rescan repairs old rows (removes rather than substitutes — "A-Game Thermal" would be an invented product name; "A-Game" is less specific and true). Word boundaries are load-bearing: `HYDRO` must not match inside `HYDROLite`
- **Analysis NEVER writes construction — it is owner-only.** `_apply_construction` is a documented no-op. It used to fill a blank, and that was the same coin toss as the 2.11 override it replaced: Claude reads HYDRO vs HYDROLite off one photo unreliably (bonded seams / gel-welded logo / sweatband don't survive a front-on shot) and skewed HYDROLite. Two later changes made a guess expensive — `retail_pricing` prices HYDRO $79 vs HYDROLite $99 (**it moves money**), and 2.29 made construction a filter (**it hides hats**). A blank is an honest "nobody has looked"; a guess is indistinguishable from a typed value, and no column records which it was. **`_strip_contradicting_construction` strips ALL constructions when none is stated** — melin names read `<line> <construction>`, so a name is the same claim in the field a person reads, and the old early-return meant a blank protected nothing. `services/construction_audit.py` + `GET/POST /api/admin/constructions/{audit,clear}` undo what was already written: a report and an explicit `dry_run` action, NOT a backfill, because which stored values were guesses is unknowable retroactively. Clearing also drops the model-name suffix and a `melin retail` price derived from it (a Manual price is never touched)
- **Hat construction**: free-form text (`Hat.construction`) with structured suggestions, NOT an enum — melin ships specialty fabrics in seasonal/collab drops, and a closed list makes each one unrecordable until someone ships a migration. `hydro` / `hydrolite` remain real columns because search filters query them and a `@property` can't appear in a `WHERE` clause, but they are **derived**: `Hat.set_construction()` is the only writer of all three, and assigning the flags directly is what lets them drift (a hat reading "Thermal" still matching a HYDRO filter). Substring match, HYDROLite checked first since it contains "hydro". Pre-2.11 clients still sending the booleans are folded in — at the schema for `HatCreate`, in `hat_service.update_hat` for `HatUpdate` (which needs the hat's current state, because `{"hydrolite": false}` means "not HYDROLite", not "no construction"). Suggestions: `GET /api/meta/constructions` merges `KNOWN_CONSTRUCTIONS` with the distinct values in use
- **Upload caps**: `copy_upload_capped` (strict, 413) guards the two single-file photo routes — the hat photo and the logo (the case photo was the third and no longer exists) — and `read_capped` (lenient) guards bulk import. `POST /share` spools each file to a temp dir in capped chunks and hands `create_job` **paths**. It previously read whole files into memory AND passed bytes — which `create_job` cannot use (`source.stat()`, `shutil.copy2(source, …)`), so every Android share raised AttributeError on the first file. Unbounded and broken, with no test covering the handler, which spools each file to disk as it arrives rather than buffering the batch. Peak RAM on any upload path is one chunk or one file, never a collection
- **`owner_notes`** is the only free-text field on a hat that no automated path writes — not analysis, not a refresh, not a bulk re-analyze. Every other prose field (`design_notes`, `style_descriptor`, the color names) is derived and gets rewritten, so the card says outright that this one survives
- **`CONDITION_LABEL` is exported from `lib/valuation.ts`** in TWO casings that are deliberately different, not duplicates: `CONDITION_IN_SENTENCE` (lowercase, goes inside a sentence) and `CONDITION_LABEL` (title case, for chart legends and table rows). Stats and Valuation each had their own copy, one named `CONDITION_LABELS` — differing from the other by a single trailing `s`
- **Adding a Hat column**: model + `_HAT_COLUMN_DDL` + `HatRead` + `types/index.ts` (+ `HatUpdate` if the UI edits it). Skipping a step is silent: a column missing from `HatRead` is invisible to the UI, one missing from the DDL bricks every hat read on an upgraded DB, and one missing from all of them is just dead weight (`custom_style_detail` sat unread from the initial commit until a review found it). There is deliberately **no** hand-written ORM→schema mapper: `HatRead` is `from_attributes=True` and `_hat_to_read()` is just `HatRead.model_validate(hat)`. Values that aren't columns (`wear_count`, `case_display_id`, `case_type`, `room_id`, `room_name`) are `@property` on the `Hat` model beside `display_id`, so nothing outside the model walks `hat.case.room`. `tests/test_hats.py::test_hat_read_exposes_every_derived_field` pins all of them plus the unassigned-hat null case
- **SQLite tuning**: WAL + `busy_timeout` on connect (`database.py`), so a transient `database is locked` waits rather than raising — important for the import worker + background loops on a Pi. **`synchronous=FULL`, reversing the earlier `NORMAL`.** `NORMAL` is SQLite's own WAL recommendation and is safe from CORRUPTION, which is what most guidance means by safe — it is NOT safe from LOSS: the WAL is synced at a checkpoint, not at commit, so a committed transaction "might roll back following a power loss" and the default 1000-page threshold means what is at risk is every write since the last checkpoint, not the last one. This deployment proved it is not theoretical: an unclean shutdown destroyed Caddy's private key on the same SD card and broke HTTPS for 37 days. `FULL` costs one fsync per commit, which for a personal inventory doing a handful of writes per interaction is not a close call. `HEADROOM_SQLITE_SYNCHRONOUS` overrides it; anything outside `SYNCHRONOUS_MODES` falls back to `FULL` rather than through, because the value is spliced into a PRAGMA (which cannot take a bound parameter) and a typo must not quietly disable durability. `checkpoint_wal()` runs LAST on shutdown — the workers above it still commit as they stop
- **Single-process by design**: rate limiter, passkey challenge store, import queue, **analysis queue**, token caches, mDNS singleton are all in-memory and process-local. `>1` worker silently breaks passkey login/rate-limiting/import dedup; the lifespan warns when `WEB_CONCURRENCY`/`UVICORN_WORKERS` > 1
- **Valuation is ONE rule, in `frontend/src/lib/valuation.ts`**. It was three (home page, valuation page, `report_service`) and all three had drifted — the home page's caption named multipliers that by then applied to almost nothing, and the report labelled a scraped median "manual". **The listed price IS the sale price**: melinrecap is a fixed-price Treet marketplace with automatic drops, so nothing is discounted off it. Comparability comes from FILTERING, done upstream in `melin_recap.fetch_resale_stats`, which matches listings on the hat's own condition and size (both are in `publicData` and were ignored until 2.21) and widens most-specific-first only when the sample is too thin. The `ASK_TO_SOLD` haircut and `CONDITION_VS_MARKET` multiplier this replaced were measurably wrong against 706 live listings and unnecessary with the real number in the feed. Signal order is `manual` (used as-is) → `comp` (model+condition+size median, used as-is) → `retail` (`RETAIL_RETENTION` share of new — still a heuristic, but only when there is no market data) → `category` → `none`. `retail` deliberately outranks `category`: retail is about THIS hat. `valueHat` returns `null`, never 0, for an unpriced hat. `CASH_PAYOUT` (0.80) / `CREDIT_PAYOUT` (1.10) are what the marketplace pays a SELLER, read off `publicData.payoutInfo`; market value and what reaches you are different numbers. `services/valuation.py` mirrors it for the server-rendered report — **including `value_cases()`**, which was first written into `report_service` as a THIRD statement the parity check could not see, and had already drifted (flat constant per row vs the browser summing each case's served `retail_price`); `tests/test_valuation_parity.py` fails if they diverge
- **`resale_price_scope`** (`manual`/`model`/`category`) records what `resale_price` is a price OF. `resale_price_source` says the same thing inside a display sentence, and branching on prose would silently revalue the collection the day someone reworded the label. `manual` is set by `hat_service.update_hat` (the one writer every client PUT funnels through) and makes the price immune to analysis overwrites — both `refresh_melin_resale` and `_apply_resale_pointer` bail on it. That second one mattered: it assigned the pointer's `None` price unconditionally and relied on the live refresh restoring a number, so an outage during an unattended re-analyze silently erased hand-entered prices
- **Find duplicates**: `services/duplicate_service.py` + `GET /api/search/duplicates` + `/duplicates` page. Groups ACTIVE hats on identity fields, never pixels (two shots of one hat differ; two different hats in one colorway don't). `exact` = every field agrees; `likely` = same model+size with the colorway missing on a side — colorways that actively DISAGREE are never grouped, or every normal shelf reads as a mistake. Requires a model_name (or brand+colorway) or un-analyzed hats all match each other. Reports only; never deletes
- **Dropdown lists must be portalled**: `components/common/AnchoredList.tsx` renders picker lists into `<body>` via `portalToBody` and positions them against their input. A list positioned inside the form is CLIPPED by `.card { overflow: hidden }` — cut off mid-row, options below unreachable, and no z-index helps because the pixels are never drawn. Two consequences of leaving the tree: hold the anchor in STATE (a ref is null on the render that first opens the list) and treat `.hr-combobox-list` as "inside" in the click-outside handler, or pointerdown on an option closes the list before the option's mousedown lands. Heights measure against `visualViewport`, so the list clears the keyboard
- **Case picker ordering**: the 3 newest cases are pinned above the room groups (`RECENT_COUNT`) and removed from those groups so nothing lists twice; suppressed once a query is typed
- **Cases show a collage** of their hats, not a case photo — every case looks the same from outside, so the picture carried no information. `components/cases/CaseCollage.tsx` is the single component; the grid feeds it `CaseRead.hat_thumbs` (up to 4) and the detail page feeds it the case's own hats. **There is no case-photo feature at all**: no upload route, no uploader on the detail or edit pages. It was removed in two stages and that is worth knowing — the grid changed first while the detail page, the edit form and `POST /api/cases/{id}/photo` kept the feature alive, so a case with three hats rendered a screen-filling "NO PHOTO" box above its own contents. `tests/test_photos.py::test_there_is_no_case_photo_route` pins the removal. The vestigial `Case.photo_path` column is still there and unread — dropping it is destructive, so it is a decision rather than a side effect
- **Home carousel is two-up on desktop, one-up on mobile** — `lib/useMediaQuery.ts` (`useSyncExternalStore`, not `useState` + effect, which renders one frame at the wrong size and pops from one hat to two on every mount). The COUNT is decided in JS rather than by hiding a second slide in CSS, so a phone never downloads a photo it won't show — that's the whole reason this isn't a pure media query, and the tests exist to keep it that way. `visibleCount` is clamped to the number of hats WITH photos (a one-photo collection rendering the same hat twice reads as a bug), and the arrows hide when `length <= visibleCount` — stepping by a screenful through a 2-hat list lands back where it started, so the old `length > 1` guard left arrows that appeared to do nothing. jsdom has no `matchMedia`; `test/matchMedia.ts` installs a stub that answers "no match" by default (the mobile-first base case, so existing tests are unaffected) and `setViewportWidth()` opts a test into a width
- **Bottom nav vs the keyboard**: iOS positions `fixed` elements against the VISUAL viewport, so the nav rides up to mid-screen over whatever is focused. `lib/useKeyboardOpen.ts` (mounted once in AppShell) watches `visualViewport` — the only thing that reports this, since no `window` resize fires — and sets `body.hr-keyboard-open`, which hides the nav. Applies to every input; the earlier per-combobox fix missed plain `<select>`s
- **Build stamp**: `.dockerignore` excludes `.git` and the frontend stage only receives `frontend/`, so nothing in the image can learn the commit — `scripts/stamp-build.sh` writes `HEADROOM_BUILD_SHA` into the `.env` compose reads automatically, and `setup.sh` installs git hooks so a pull keeps it current
- **Free-text vocabulary**: `services/vocabulary.py` keeps `construction` and `artist_series` from splitting into five spellings of one thing. Two layers — `GET /api/meta/{constructions,collections}` suggests what's in use, and `canonicalize()` on write snaps a typed value to the spelling already on record (curated `KNOWN_CONSTRUCTIONS` checked first, since it's authoritative before any hat uses it). Folds case, whitespace AND accents ("Piña" = "Pina" = "PINA" — one drop typed with and without a long-press). `_preferred()` is the single tiebreak used by BOTH the write path and the merge: curated spelling → most accents (adding one is deliberate, dropping one is a slip) → most common → alphabetical. On write the value on record wins ties; the typed one only wins when it carries accents the stored one dropped. Matching is in Python, not SQL — SQLite's `lower()` is ASCII-only and would silently skip every accented row. `merge_case_variants()` repairs pre-existing variants, run once from lifespan behind `vocabulary_merged_v1`
- **Case capacity**: `services/capacity.py::evaluate` is the ONE rule — used by `hat_service._validate_capacity` to enforce it on write and by `routes/cases._case_to_read` to publish `accepts_*` / `free_*` / `overfull` / `nominal_capacity` for the picker. Two implementations would drift, and a picker that disagrees offers a case the save rejects with 409. Occupancy excludes disposed hats (they free their slot)
- **Case picker**: `components/hats/CasePicker.tsx` — searchable, grouped by room, greys out cases that would 409 with the reason. Replaced a `<select>` that became a 60-row iOS picker wheel. Any dropdown-style picker must call `usePickerOpen`, which hides the fixed bottom nav while open (z-index 100, and iOS rides it up to mid-screen when the keyboard opens)
- **Beanie shapes are styles, and `is_beanie` has ONE definition.** melin names its beanie shapes like any other model (Journey, Destination, All Day — its own "Beanie Shape Guide"), so they are `HatStyle` members, not one bucket. `Hat.is_beanie` is a real column (search filters query it, capacity depends on it) **derived** from style, so `schemas/hat.BEANIE_STYLES` + `is_beanie_style()` are the single definition — same reasoning as `Hat.set_construction` owning hydro/hydrolite. A shape missing from the set packs 3-to-a-case instead of 8, vanishes from the Beanies filter, and makes the picker offer cases the save then 409s. `GET /api/meta/styles` **publishes `is_beanie` per option** rather than letting the frontend re-derive it: the flag decides which cases the picker offers, and a hardcoded TS list would be a second definition. `beanie` remains as "Beanie (unspecified)" — existing rows use it and an unidentified shape is a real state
- **Domain model**: Rooms contain Cases contain Hats — **and Rooms can contain Hats directly** (2.33). A hat kept on a shelf, a hook or a stand has `direct_room_id` and no case; `Hat.room` resolves either, so readers didn't change. The two are **mutually exclusive** — `assign_hat` clears one when it sets the other, because a cased hat's room IS its case's room. Any style may be room-stored (Caddies and Aviators don't fit a travel case at all, but nothing is restricted). Anything filtering hats by room must cover BOTH — `search_service._in_room()` is that disjunction, and `Hat.room_id` being a `@property` means it cannot appear in a `WHERE`; filtering only through the case silently excluded every room-stored hat while the client-side Hats filter kept showing them. `delete_room` moves caseless hats as well as cases. Cases are type-exclusive. **Full vs overfull are different states**: the default is 3 regular hats OR 8 beanies, and `OVERFILL_ALLOWANCE = 1` lets one more REGULAR hat in, accepted on write and reported as `overfull`. **Beanies get `BEANIE_OVERFILL_ALLOWANCE = 0`**: 3 is melin's *name* for the case ("3 Hat Travel Case") so a 4th demonstrably fitting was never a measurement, where 8 is what the owner counted packing one — slack on top of a measured maximum would assert a 9th fits. `free_*` counts down to NOMINAL and hits 0 at full, so the picker renders occupancy from `nominal_capacity`, never `used + free` — the latter shows a 4th hat in a 3-hat case as "4/4". The 409 quotes `limit_*`, not `max_*`. A per-case `capacity` override gets **no** allowance: the field exists for "a case you don't want to cram", so a stated number is exact. Exactly one room carries `is_default` — it's the fallback orphaned cases move to and the room new cases land in when none is named, so it's the only room that can't be deleted. Any room can take the role (`POST /api/rooms/{id}/default`), which frees the previous one for deletion; `database.ensure_default_room()` repairs the invariant on boot. Deliberately a flag, not a hardcoded `id=1`. Disposed hats stay in the DB but free their case slot
- **Hat photo pipeline**: Upload → Pillow resize/HEIC convert (JPEG, off the event loop — **retained as `original_path`**, the only thing a re-cut can work from) → `rembg` background removal (transparent PNG, becomes canonical) → 320px WebP thumbnail (`thumb_path`, what the grids render) → Claude Vision tool-use → eBay refresh (best-effort) → Melin resale → persist. Per-stage timing is logged (`hat=… rembg=…s claude=…s`)
- **Pipeline degradation**: Each step (bg-removal, Claude, eBay) can fail without breaking the others; failures land in `hat.analysis_status` (`ok` / `skipped` / `error` / `fallback`) with `analysis_error` text. eBay errors are logged but never block.
- **Analysis fallback**: When Claude is unconfigured OR errors, `run_fallback_analysis()` applies mask-derived colors (PNG canonical only — background rejected by construction) plus a Google Vision logo brand when that key exists → `analysis_status='fallback'`. Produces nothing → prior `skipped`/`error` state stands. Never sets model_name/price; eBay comps stay Claude-gated.
- **Bulk import**: `import_service.start_worker()` runs from lifespan. Items processed one-at-a-time. The worker loop survives ANY per-item exception (never dies). On boot, `_recover_on_boot()` re-queues items stranded in `processing`, recomputes counters, and closes jobs whose items are all terminal (e.g. all-oversize). Cancelled jobs are never flipped back to `done`. The upload route caps per-file (chunked read) and total-batch bytes to bound RAM.
- **Activity log / audit**: `log_activity(db, kind=, entity_type=, entity_id=, summary=, details=)` is fire-and-forget; failures swallowed; **caller commits** (failed-login and other pre-exception paths must commit explicitly before raising). Covers auth events (login success/failed/blocked, password change, token rotation, passkey add/remove), backup downloads, key/cred changes, and share-link create/revoke. Daily prune task in lifespan.
- **Auth**: argon2id passwords verified/hashed OFF the event loop under a concurrency bound (`verify_password_async`/`hash_password_async`). Login rate-limited per (ip, username), in-memory, with empty-key cleanup. First-run `/api/auth/setup` is serialized against a concurrent second POST via an `app_settings` PK sentinel (no duplicate owners). **Password change rotates the API token** as well as revoking other sessions (complete compromise response)
- **API key resolution**: `settings_service.get_anthropic_key()` checks DB first (UI-managed), then env (`HEADROOM_ANTHROPIC_API_KEY`). DB always wins. Same for `get_anthropic_model()` and eBay `get_creds()`. Set/clear via public `set_setting`/`get_setting`
- **API key safety**: Routes return only `ApiKeyStatus` (configured / source / masked prefix+suffix) — the raw key never goes back over the wire. Same for eBay creds
- **Readiness redaction**: `GET /health/ready` is unauthenticated (Docker healthcheck) — it returns booleans only for anonymous callers (no fs paths, key source, or raw error text); authenticated callers get full detail plus an import-worker liveness canary
- **Readiness gates on free space and worker liveness**, not just "is it writable". The old probe wrote two bytes, and two bytes fit on a volume with 8KB free while a 200MB tarball doesn't — `utils/disk.py` has two thresholds saying two different things (`low` = warn, `ok=False` = readiness fails below `HEADROOM_DISK_MIN_FREE_MB`, an absolute floor because what matters is whether the next backup fits, which is a size not a share). Worker liveness is gated on `worker_expected()` (the env flag) rather than `worker_alive()` alone — the latter is False for a *disabled* worker too, and the test suite runs with both off. Together these are the only reason the container can go unhealthy for the two failures most likely across weeks of unattended running; `restart: unless-stopped` was structurally blind to both. A broken measurement reports `ok=True` — a health signal that fails closed is worse than none
- **`add_middleware` PREPENDS**, so the LAST added is OUTERMOST. `SecurityHeadersMiddleware` must be added last or the auth gate's 401 short-circuits before reaching it — an anonymous `GET /api/hats` came back with two headers, no CSP, no nosniff, no X-Frame-Options, for two years. `BodySizeLimitMiddleware` (`limits.py`) sits outside even that: non-multipart bodies over `HEADROOM_MAX_BODY_BYTES` (2MB) are refused with 413 before the gate spends a DB lookup on them. Multipart is deliberately exempt — those routes stream to disk under their own much larger caps. Bytes are counted as well as `Content-Length` checked, since a chunked request declares nothing
- **Errors are durable**: `error_handler.log_unhandled` writes an `error.unhandled` activity row for every unhandled exception, then Starlette re-raises so the traceback still reaches the container log. It resolves the session through `request.app.state.session_factory` (the seam tests swap), not the module-level `async_session`. `validation_error` strips `input`/`ctx`/`url` from 422 bodies — pydantic puts the offending value in every error and FastAPI serializes it, so a password rejected as too short was echoed back in clear text. Note when testing: a route added AFTER `create_app` is shadowed by the SPA catch-all, so failure tests must break a real route
- **Secrets never go in a URL**: httpx logs the full request URL at INFO, so `?key=` put the Google Vision credential in the container log on every fallback analysis. It goes in `X-Goog-Api-Key` now
- **Disposition (soft delete)**: `dispose_hat()` sets `disposed_at` + 4 metadata columns. `_validate_capacity` and `_get_next_position` skip disposed hats. `undispose_hat()` restores AND **reassigns `position_in_case`** so it can't collide with a hat added while it was disposed. If the case is full it lands unassigned. Default `GET /api/hats` filters to `status=active`; `?status=disposed`/`?status=all` available
- **Wear log**: one row per hat per day; unique `(hat_id, worn_at)` constraint + IntegrityError-tolerant insert make the "wearing this today" tap idempotent even under a double-tap race
- **Search**: Multi-term AND across style/condition/size/colors/room/brand/model_name/artist_series/construction; disposed hats excluded. Default searches `general_color` (normalized to the palette via `normalize_hex_name` — at analysis time, at the one-time startup backfill flagged `color_names_normalized_v1`, AND on manual `PUT /api/hats/{id}/colors` edits); `exact_colors=true` searches `color_name`
- **Color terms match MAJOR colors by default** (`search_service.MAJOR_COLOR_RANK = 2`, `COLOR_SCOPES = major|accent|all`). Matching every swatch made color search useless here — every melin hat is a dark crown with a bright logo, so "pink" returned every black cap with a pink mark and the accent colors are precisely the ones that vary. Keyed on `dominance_rank`, not `tier`, for the same reason the similarity ranking is. **`dominance_rank` is assigned POSITIONALLY by every writer** (`enumerate(start=1)`), so a test that states a rank in the payload is silently ignored — build fixtures by order
- **`.card` declares `display: block`.** It is applied to an `<a>` in six places, and an anchor is inline by default: `h-100` is ignored and the border breaks across line boxes. Invisible for years because every card was a `<div>`; it surfaced the moment 2.37 made the guest tiles links
- **A public search must only match fields the caller can SEE.** `search_hats(public_fields_only=True)` drops the `condition` / `size` / `artist_series` / `construction` clauses **and the hydro/hydrolite flags derived from construction**, because matching on a field the projection withholds turns search into an ORACLE for it — `?q=worn` returned exactly the worn hats, so a guest could read every hat's condition by probing. Guest search also uses `GUEST_SEARCH_LIMIT`, not the owner's 50, because the response reports its own length as the match count and a truncated list makes that count a lie (the `len()`-of-a-capped-list mistake, made three times now: colorway catalog, analysis `pending_count`, this)
- **Color-similarity search**: `GET /api/search/color?hex=` — **membership is CATEGORICAL, ranking is by distance.** It used to be a CIEDE2000 distance under a cutoff, tuned three times (30 → 22 → 26) and wrong every time. The measurement that settles it: within-family palette distances reach **ΔE 55.8** (light blue→navy, both plainly blue) while cross-family ones start at **15.4** (black→navy) — the ranges *invert*, so no threshold can keep the first and reject the second. At 26, **51 cross-family pairs matched** (black/navy, silver/beige, white/cream) and every search returned most of the shelf. `color_extraction.is_same_color()` now decides membership on the curated names via `families_of_lab()` (every palette entry within `FAMILY_AMBIGUITY_MARGIN = 5` of the nearest — a margin asking "is this classification ambiguous?", not "is this color close?"; saturated targets always resolve to exactly one family, only muted swatches come out ambiguous). `_COLOR_FAMILIES` maps a name to a SET, because charcoal is both a soft black and a dark grey and forcing it into one bucket makes the other search wrong. **Muted swatches fall back to HUE ANGLE**: a dark teal is nearest *charcoal* by ΔE because ΔE is dominated by lightness, but its hue is 197°, identical to a mid teal's. That fallback is gated by the pre-existing chroma-ratio guard (`is_neutral_mismatch`) — a dark teal keeps 41% of teal's chroma, a blue-grey 20% of blue's, and their absolute chromas are 11.1 and 11.7, so nothing but the ratio separates them — and blue/purple is vetoed outright (`_INCOMPATIBLE_FAMILIES`) because CIELAB's hue angle is non-linear through the blue region. Distance now only ORDERS matches, with `_RANK_DISTANCE_BUDGET` (rank 1 unlimited — being the right color IS the question; rank 2 ≤ 18, deeper ≤ 12) so a pink brim still counts and a pinkish logo doesn't. `ColorSearchResult.distance` is the raw ΔE and is NOT the sort key; `matched_rank` explains why a Δ0 accent sits below a Δ5 primary. Palette chips from `GET /api/meta/colors`
- **Certificate lifetime has a hard ceiling at 825 days, and it is Safari's.** `Caddyfile` (bind-mounted by the https-lan overlay) issues an **820d** leaf via `tls { issuer internal { lifetime 820d } }` plus `pki { ca local { intermediate_lifetime 3000d } }`. Caddy's default is **twelve hours**, which is a fine default until renewal stops — it did, an unclean shutdown ate the stored leaf key, and Caddy re-queued a renewal every ten minutes for **37 days** while serving the expired cert. **A Caddyfile rather than `caddy reverse-proxy` because the CLI cannot express PKI options at all**, so the default was not overridable in the old form. The numbers are not free choices: Safari (so every iPhone) rejects a server certificate whose validity exceeds **825 days** even under a manually installed root — the quoted 398-day cap is a *different* rule covering only Apple's PREINSTALLED roots — and **Chrome and Firefox impose no limit here**, so a 10-year cert works on the laptop you test from and fails on every phone with what looks like a trust-store error. The intermediate must clear `renewal_window_ratio` (1/3) × the leaf and stay under the 3600d root; `tests/test_tls_health.py` pins both, since the second surfaces only as a sidecar that won't start. **The ROOT is untouched by any of this** — changing `intermediate_lifetime` reissues the intermediate, which is presented during the handshake, not the self-signed anchor in each keychain, so no device reinstalls. `docker-compose.https.yml` keeps the CLI form deliberately: Let's Encrypt sets its own 90-day lifetime, so there is nothing to choose. **Shipping that config does NOT fix an existing install, and the failure is silent.** Caddy loads the intermediate it already has and only regenerates one when it is expiring, so every box that ran the overlay before 2.48 kept a **7-day** intermediate (the old default) and quietly logged `cert lifetime would exceed issuer NotAfter, clamping lifetime` — 820 days requested, ~6 granted, because a leaf cannot outlive its issuer. The real deployment ran that way for days. The repair is to delete the intermediate AND both issued leaves (they are signed by it, so replacing the issuer alone leaves a chain that does not build) then restart Caddy; **the root is untouched, so no device re-trusts**. `ca_vault.clamped_by_issuer()` detects it — a clamped leaf's expiry matches its issuer's to the second — because the two failures look identical on the certificate and have opposite fixes: renewal repairs an old leaf and can never repair a clamped one, and the Trust-this-device card used to advise the restart that loops
- **`.local` never crosses a VPN, and the failure presents as an outage.** mDNS is link-local **multicast**: no server holds the record, so `headroom.local` cannot resolve over Teleport/Tailscale/WireGuard or across a routed subnet, and there is no DNS anywhere to point at it. The IP is not a fallback for two compounding reasons — **Caddy rejects a TLS handshake whose SNI matches no configured site** (`curl --resolve headroom.local:443:<ip> https://headroom.local/` → 200 while `curl https://<ip>/` → **000**, no response, even with `-k`), and the certificate carries `DNS:headroom.local` with **no IP SAN**, so the name check would fail anyway. **The trap is Caddy's automatic HTTP→HTTPS redirect**: `http://<ip>/` answers **308 → `https://<ip>/`**, the one address that cannot complete a handshake, so the first thing anyone tries hands back the thing that is broken and the server reads as down. Fix: `Caddyfile`'s site line is `{$HEADROOM_SITE_ADDRESSES:headroom.local}` — comma-separated, defaulting to the mDNS name so existing installs are unchanged; listing the LAN IP makes Caddy serve it AND sign it into the cert as an IP SAN under **the same root**, so already-trusting devices need no reinstall. **Passkeys stay bound to `HEADROOM_ORIGIN`** — WebAuthn credentials are per-origin, so one registered at `https://headroom.local` is not offered at `https://<ip>`; that is WebAuthn working, not a misconfiguration, and no certificate change fixes it (password login works on both). The zero-config remote path is **`http://<ip>:8000`**, which is uvicorn direct and bypasses Caddy entirely — no secure context, so no passkeys there either
- **Path traversal protection**: one shared implementation in `utils/paths.py` (`safe_join` / `safe_file`), not two copies. `_safe_spa_path()` is a thin wrapper over it defending the SPA fallback against `/%2e%2e/data/headroom.db`-class attacks; the share-photo streamer calls `safe_file` directly
- **URL-seeded filters**: the Cases type filter lives in the URL (`/cases?type=archive`, `replace: true` so tapping through filters doesn't build a back stack); `useHatFilters` and Search seed from query params (`?style=`, `?color=`, `?q=`) **once**, as initial state — the controls own it afterwards, since a two-way binding fights the user every time they widen a filter a link had set. `useHatFilters` also opens the filter bar when a link arrived with filters, so the reason the list is short is on screen
- **Query keys**: `['hats', 'disposed']` is a SIBLING of `['hats']`, not covered by it — Valuation and Stats need what has left the collection for realized totals, and it must never be summed with the active list. `['rooms']` for full `RoomRead[]`, `['room', id]` for one room's CONTENTS (a **sibling** of `['rooms']`, not covered by it — "rooms" is not a prefix of "room", so `invalidateHatViews` lists both), `['meta', 'rooms']` for dropdown options — invalidate all three on room mutations. **Anything that changes a hat's existence, disposition or case membership must go through `lib/invalidate.ts::invalidateHatViews`** — `['cases']` carries the occupancy counts, `['case', displayId]` the case's own hat list and `['rooms']` the per-room counts, and mutations that invalidated only `['hats']` left all three stale for the 30s `staleTime`. `['case']` is passed as a bare prefix so every mounted case detail is covered. `['settings', 'api-key']`, `['settings', 'google-vision-key']`, `['settings', 'model']`, `['settings', 'mdns']`, `['settings', 'tls']`, `['settings', 'tags']`, `['settings', 'guest-view']`, `['guest-collection', q]`, `['admin', 'recent-errors']`, `['admin', 'recent-errors-count']`, `['admin', 'activity']`, `['admin', 'ebay']`, `['admin', 'import-jobs']`, `['admin', 'import-job', id]`, `['admin', 'analysis-queue']`, `['admin', 'backups']`, `['admin', 'purchases']`, `['settings', 'logo']`, `['auth', 'me'|'status'|'passkeys']`, `['share-links']`, `['meta', 'colorways']` (and `['meta','colorways','models']`), `['meta', 'constructions']`, `['admin', 'colorway-status']`, `['duplicates']`, `['hat', id]`, `['public-share', token]`. Not exhaustive — `['meta', …]` has an entry per lookup (colors/styles/sizes/conditions/collections/rooms). Note `['admin','recent-errors']` does NOT prefix-match `['admin','recent-errors-count']` — the nav badge is a sibling key and needs its own invalidation

## Conventions

- Routes in `src/headroom/routes/`, register in `routes/__init__.py`. **Order matters** when paths overlap — `/api/hats/import` must register before `/api/hats/{hat_id}` so the path parser doesn't shadow it
- `@pytest.mark.anyio` for async tests, asyncio backend only (no trio). Sync tests in this codebase need `pytestmark = pytest.mark.anyio` because the autouse `setup_db` fixture is async. The `anyio` marker comes from the `anyio` package's pytest plugin (no separate `pytest-anyio` dependency)
- Dev dependencies in `[dependency-groups] dev` in pyproject.toml
- Frontend API functions in `frontend/src/api/`, types in `frontend/src/types/`
- `datetime.now(timezone.utc)` over the deprecated `datetime.utcnow()`
- **JSX separators**: use the literal Unicode `·` in `<option>` labels, not the HTML entity `&middot;` — JSX renders entities inside expressions literally, so the entity shows up as raw text in the dropdown
- Dockerfile must run as a non-root `USER` (semgrep-enforced). **Dependencies install from `requirements.txt`, the PROJECT from `uv sync --frozen`** — that split is a measured 490s of an 873s Pi rebuild. `pyproject.toml` carries the `version` field, so cutting a release used to bust the dependency layer (`uv sync` 237s) and the rembg model layer beneath it (149s) for a string that has nothing to do with dependencies; `requirements.txt` is `uv export --no-emit-project`, byte-identical across a version bump, so both now survive one. `--require-hashes` keeps the supply-chain guarantee `--frozen` gave. **The version-bearing copies must stay AFTER the dependency install** or the whole thing silently reverts — `tests/test_requirements_export.py` pins that ordering and fails on drift from `uv.lock`. Regenerate with `uv export --frozen --no-dev --no-emit-project --format requirements-txt -o requirements.txt` whenever dependencies change. **A Dependabot PR touching backend deps is a starting point, not a mergeable change** — it cannot see that `requirements.txt` is DERIVED, so it either bumps that file alone (a transitive like `websockets`, which `uv.lock` never moves for) or bumps both to *different* resolutions (observed: lock said `annotated-types 0.7.0`, the same PR's requirements.txt said `0.8.0`, and `cbor2` was in one and not the other). Never fix one by regenerating on its branch — in the second case that silently discards half the update. Take the whole thing on your own branch with `uv lock --upgrade` + the export above, and close the Dependabot PRs as superseded. There is deliberately no auto-regenerating workflow: it needs `pull_request_target` plus a checkout of the PR branch, which is the pwn-request pattern this repo's own semgrep scan rejects
- **Rules of Hooks**: every `useState` / `useMemo` / `useEffect` / `useQuery` must run on every render — never call hooks after an early `return`. Common bug source on pages with `if (isLoading) return <Spinner />` followed by a derived `useMemo`
- **Mobile bottom-nav layout**: `.bottom-nav` uses `display: flex` with `flex: 1 1 0` items. The `.d-lg-none` utility class **must not** force `display: initial` at mobile breakpoints — that overrides the flex and stacks tabs vertically
- **Dependency updates are automated**: `.github/dependabot.yml` opens weekly PRs for npm, uv, Docker base images (incl. the `COPY --from=` uv pin) and Actions, with a 7-day cooldown mirroring `[tool.uv] exclude-newer`. Minor/patch are grouped into one PR; majors come individually. `.github/workflows/ci.yml` runs pytest + typecheck + production build + a real Docker build & health check on every PR, so those bumps verify themselves.
- **Releasing**: bump `pyproject.toml` AND `frontend/package.json` together, run `uv lock`, refresh `frontend/package-lock.json` (`npm install --package-lock-only`), regenerate `requirements.txt` if dependencies changed, and add a `CHANGELOG.md` entry (Keep-a-Changelog; a **Breaking** section justifies a major bump — e.g. build-arg renames, `--frozen`, auth behavior changes). Vite bakes the package.json version into the bundle as `__APP_VERSION__`. Cut the release with a `vX.Y.Z` git tag + `gh release create` (2.0.0 onward)
- **Merging/tagging from a worktree**: `main` is checked out by the primary clone, so anything that wants to switch to it locally fails with `fatal: 'main' is already used by worktree`. In particular `gh pr merge --delete-branch` **merges on the server first and only then fails** on cleanup — the error looks like the merge didn't happen when it did, so check `gh pr view <n> --json state` before retrying. Do the cleanup without a checkout instead: `gh pr merge <n> --squash`, then `git push origin --delete <branch>`. Tag by SHA rather than by branch — `git tag -a vX.Y.Z <merge-sha>` — since `git tag` on a branch you can't check out is the same trap
- **Env vars of note**: `HEADROOM_MDNS_ENABLED`/`_HOSTNAME`/`_PORT`/`_INTERFACE` (LAN discovery; `_INTERFACE` pins the zeroconf bind interface — defaults to the detected LAN IP so a Docker host-net container doesn't leak the responder onto docker0/veth, `all` restores all-interfaces), `HEADROOM_BUILD_SHA` (footer build stamp / Docker build-arg), `HEADROOM_BACKUP_*` (incl. `_KEEP`, a count — see `backup_service`; `_INCLUDE_CA`, default true, puts Caddy's CA **private keys** in the archive — see `ca_vault`), `HEADROOM_MAX_BODY_BYTES` (2MB, non-multipart only), `HEADROOM_DISK_MIN_FREE_MB`/`_WARN_PCT` (readiness floor / log warning), `HEADROOM_IMPORT_WORKER_ENABLED`, `HEADROOM_ANALYSIS_WORKER_ENABLED`, `HEADROOM_REMBG_CONCURRENCY` (concurrent rembg inferences, default **1** — both workers reach `remove_background` and a 179MB model plus a full-res decode is the app's largest allocation), `HEADROOM_MEM_LIMIT` (container memory ceiling, default 1g), `HEADROOM_REMBG_MODEL` (default `isnet-general-use` — `u2netp` is faster but cuts hat bills off), `HEADROOM_RP_ID`/`HEADROOM_ORIGIN` (passkeys). The retired `HEADROOM_ADMIN_TOKEN` is ignored
